# ТЗ: Консольный клиент-серверный чат на Node.js

## 1. Цель задачи

Написать простой многопользовательский чат: один сервер и произвольное число клиентов. Клиенты подключаются к серверу по IP и порту, общаются в общем чате, интерфейс работает в терминале.

После выполнения задачи ты должен понимать:

- как устроена клиент-серверная архитектура и чем отличаются роли сервера и клиента;
- жизненный цикл соединения: установка, обмен сообщениями, штатное закрытие, обрыв;
- что такое WebSocket, как он устанавливается поверх HTTP и что работает под ним (TCP);
- как Node.js обслуживает много клиентов одновременно в одном потоке (event loop, неблокирующий ввод-вывод);
- как организовать простой прикладной протокол поверх транспорта.

Основная часть делается на WebSocket. В дополнительном задании (раздел 11.1) транспорт переписывается на чистый TCP, чтобы разобраться, что WebSocket делает за тебя.

## 2. Ограничения по технологиям

- Язык: JavaScript (или TypeScript), Node.js LTS.
- Сеть: библиотека [`ws`](https://github.com/websockets/ws), и на сервере, и на клиенте.
- Терминал: встроенный модуль `readline`.
- Разбор аргументов: вручную через `process.argv` или встроенный `util.parseArgs`.
- **Запрещено:** `socket.io` и другие надстройки с готовыми комнатами, рассылкой и переподключением. Рассылку всем клиентам, учёт участников и обработку отключений нужно написать самому.
- Прочие внешние пакеты допустимы только для мелочей (например, цвета в терминале), но лучше обойтись без них.

## 3. Состав проекта

```
chat/
├── server.js        # логика сервера: участники, рассылка, команды
├── client.js        # логика клиента: UI, команды
├── protocol.js      # общий код: формирование и разбор сообщений
├── transport/       # всё, что связано с ws, изолировано здесь
├── package.json
└── README.md        # как запустить + ответы на вопросы из раздела 9
```

**Важно для архитектуры:** работа с `ws` должна быть изолирована в слое транспорта. Логика чата (ники, рассылка, команды) не должна знать, что под ней WebSocket. Тогда в доп. задании 11.1 замена на TCP затронет только транспорт.

## 4. Запуск

### Сервер

```bash
node server.js --port 5000
```

- `--port` — обязательный, целое число 1–65535.
- Сервер слушает на всех интерфейсах, чтобы к нему можно было подключиться с другой машины в локальной сети.
- При старте выводит: `Server listening on port 5000`.
- Если порт занят (`EADDRINUSE`) или некорректен — понятное сообщение об ошибке и выход с ненулевым кодом.

### Клиент

```bash
node client.js --host 192.168.1.10 --port 5000 --nick alice
```

- `--host`, `--port`, `--nick` — обязательные.
- Клиент сам собирает адрес вида `ws://<host>:<port>`.
- Никнейм: 1–20 символов, буквы, цифры, `_`, `-`.
- При неверных аргументах — подсказка по использованию (usage) и выход с кодом 1.

## 5. Протокол обмена

Одно WebSocket-сообщение = один JSON-объект с обязательным полем `type`. Кодировка UTF-8.

### Сообщения клиент → сервер

| type    | поля   | назначение |
|---------|--------|------------|
| `join`  | `nick` | первое сообщение после подключения, регистрация в чате |
| `msg`   | `text` | сообщение в общий чат |
| `list`  | —      | запрос списка участников |
| `leave` | —      | корректный выход |

### Сообщения сервер → клиент

| type      | поля                  | назначение |
|-----------|-----------------------|------------|
| `welcome` | `users: string[]`     | успешный вход, список текущих участников |
| `error`   | `code`, `message`     | ошибка (например, ник занят) |
| `msg`     | `from`, `text`, `ts`  | сообщение чата (`ts` — время сервера, unix ms) |
| `system`  | `text`, `ts`          | системное событие: вход/выход участника |
| `users`   | `users: string[]`     | ответ на `list` |

Пример обмена:

```
C→S {"type":"join","nick":"alice"}
S→C {"type":"welcome","users":["bob","alice"]}
S→* {"type":"system","text":"alice joined the chat","ts":1729425600000}
C→S {"type":"msg","text":"Привет всем!"}
S→* {"type":"msg","from":"alice","text":"Привет всем!","ts":1729425605000}
```

## 6. Функциональные требования

### 6.1 Сервер

1. Принимает любое количество одновременных подключений.
2. Хранит список подключённых клиентов (соединение + ник). Рассылку реализовать самостоятельно — пройтись по своему списку участников.
3. Регистрация:
   - пока клиент не прислал `join`, любые другие его сообщения отклоняются с `error`;
   - если ник уже занят — отправить `error` с кодом `NICK_TAKEN` и закрыть соединение;
   - если ник невалиден — `error` с кодом `INVALID_NICK` и закрыть соединение;
   - при успехе — `welcome` новому клиенту и `system` «X joined the chat» всем остальным.
4. Сообщение `msg` от клиента рассылается **всем** зарегистрированным клиентам, включая отправителя (так клиент видит, что сообщение дошло). Сервер сам подставляет `from` и `ts` — клиенту доверять нельзя.
5. Пустые сообщения и сообщения длиннее 1000 символов отклоняются с `error`.
6. Некорректный JSON или неизвестный `type` не должны ронять сервер — логировать и отвечать `error`.
7. При отключении клиента (штатном `leave` или обрыве: закрыли терминал, пропала сеть) — удалить его из списка и разослать `system` «X left the chat».
8. Ошибка в одном соединении не должна влиять на остальных клиентов и не должна завершать сервер.
9. Логирование в консоль сервера: подключение (IP:порт), регистрация, отключение, ошибки. Текст сообщений логировать необязательно.
10. По `Ctrl+C` сервер рассылает `system` «Server is shutting down», закрывает все соединения и завершается.

### 6.2 Клиент

1. Подключается к серверу, сразу после открытия соединения отправляет `join`.
2. Если сервер недоступен (`ECONNREFUSED`, таймаут) — понятное сообщение и выход с ненулевым кодом.
3. При получении `error` на этапе входа — показать причину и завершиться.
4. Отображение сообщений:
   ```
   [14:05:12] alice: Привет всем!
   [14:05:20] * bob joined the chat
   ```
   Время берётся из `ts` сервера. Свои сообщения можно выделять (например, `you:` или цветом).
5. **Входящее сообщение не должно ломать строку, которую пользователь сейчас набирает.** Пришедшее сообщение выводится над строкой ввода, а набранный текст сохраняется. (Подсказка: `readline` умеет очищать и перерисовывать текущую строку.)
6. Команды:
   - `/users` — показать список участников;
   - `/quit` — отправить `leave` и выйти;
   - `/help` — список команд.
   - Неизвестная команда — локальная подсказка, на сервер не отправляется.
7. `Ctrl+C` работает так же, как `/quit`.
8. Если сервер закрыл соединение или связь оборвалась — вывести «Connection to server lost» и завершиться.
9. Кириллица и эмодзи отображаются корректно.

## 7. Нефункциональные требования

- Код разделён по ответственности: транспорт, протокол, логика чата, UI клиента — не одна функция на 300 строк.
- Формирование и разбор сообщений вынесены в общий `protocol.js` и используются и сервером, и клиентом.
- Логика чата не обращается к `ws` напрямую (см. раздел 3).
- Никаких `process.exit()` посреди логики без закрытия соединений.
- Нет необработанных исключений и `unhandled 'error' event` при любых действиях клиента.

## 8. Что не входит в задачу

- Шифрование (`wss://`, TLS), авторизация, пароли.
- Хранение истории в файле или БД.
- Комнаты, личные сообщения (см. доп. задания).
- Графический или веб-интерфейс.

## 10. Критерии приёмки

Проверка проводится вручную в нескольких терминалах. Для отправки произвольных сообщений удобно использовать `npx wscat -c ws://localhost:5000`.

- [ ] Сервер стартует на указанном порту; при занятом порту — понятная ошибка.
- [ ] Три клиента подключаются, видят уведомления о входе друг друга.
- [ ] Сообщение одного клиента мгновенно появляется у всех трёх.
- [ ] Повторный вход с занятым ником отклоняется с понятной ошибкой.
- [ ] Набираемый текст не «перемешивается» с входящими сообщениями.
- [ ] `/users` показывает актуальный список.
- [ ] Закрытие терминала клиента (без `/quit`) — остальные видят «left the chat», сервер продолжает работать.
- [ ] Остановка сервера — все клиенты корректно сообщают о потере соединения и завершаются.
- [ ] Клиент на другой машине в локальной сети подключается по IP сервера.
- [ ] Отправка через `wscat` мусора (не JSON, JSON без `type`, `msg` до `join`) не роняет сервер, в ответ приходит `error`.
- [ ] Сообщения на русском и с эмодзи отображаются корректно.
- [ ] Логика чата не импортирует `ws` — он используется только в слое транспорта.
- [ ] В README есть инструкция запуска и ответы на вопросы из раздела 9.

## 11. Дополнительные задания

### 11.1 Переход на чистый TCP (главное доп. задание)

Заменить транспорт с `ws` на встроенный модуль `net`. Логика чата, протокол и команды остаются прежними, меняется только слой транспорта. Если архитектура из раздела 3 соблюдена, правок вне `transport/` быть не должно.

Ключевая проблема: WebSocket передаёт **сообщения**, а TCP — **поток байтов**. Одно `socket.write()` на одной стороне не обязательно придёт одним событием `data` на другой. Сообщения могут **склеиваться** (два в одном `data`) и **разрываться** (одно на несколько `data`).

Требования:

1. Формат: одно сообщение = одна строка JSON, завершённая `\n` (NDJSON).
2. Получатель копит входящие данные в буфер, режет по `\n`, каждую полную строку парсит как JSON, а неполный хвост оставляет в буфере до следующего `data`.
3. Учесть, что многобайтовый UTF-8 символ (кириллица, эмодзи) тоже может разорваться между двумя `data`.
4. Все критерии приёмки из раздела 10 выполняются и на TCP-версии (вместо `wscat` используется `nc`).
5. Проверка склейки:
   ```bash
   printf '{"type":"join","nick":"nc"}\n{"type":"msg","text":"hi"}\n' | nc localhost 5000
   ```
   Оба сообщения должны быть обработаны.
6. В README ответить:
   - почему нельзя считать, что одно событие `data` — это одно сообщение;
   - какие изменения потребовались при переходе и сколько файлов пришлось тронуть;
   - как теперь выглядит ответ на вопрос 2 из раздела 9.

Бонус: вместо `\n`-разделителя сделать фрейминг с префиксом длины (4 байта длины + payload) и сравнить два подхода.

### 11.2 Остальное (по желанию)

1. **Личные сообщения:** `/w bob текст` — видит только bob.
2. **История:** новый участник при входе получает последние 20 сообщений.
3. **Heartbeat:** сервер раз в N секунд проверяет, живы ли клиенты, и отключает «молчащих» по таймауту. Объяснить, зачем это нужно, если обрыв и так обычно обнаруживается.
4. **Автопереподключение** клиента с экспоненциальной задержкой.
5. **Rate limiting:** не больше 5 сообщений в секунду от одного клиента.
6. **Тесты:** автотест, который поднимает сервер, подключает двух клиентов программно и проверяет доставку сообщения.

## 12. Рекомендуемый порядок работы

1. Эхо-сервер на `ws`: что прислали — то и вернул. Проверить через `wscat`.
2. Сервер рассылает всё полученное всем подключённым (ещё без JSON и ников).
3. Вынести `ws` в слой транспорта, логика работает через него.
4. Протокол: `protocol.js`, JSON-сообщения с `type`.
5. Регистрация по нику, `join`/`welcome`/`system`.
6. Клиент с `readline` и аккуратным выводом.
7. Команды, обработка ошибок и обрывов.
8. README и прогон по чек-листу приёмки.
9. Доп. задание 11.1 — переход на TCP.
