# Лабораторная 5. События: EventEmitter

**Цель:** освоить событийную модель Node.js: подписываться на события,
создавать свои классы-источники событий, правильно обращаться с событием
`error` и превращать события в промисы и асинхронные итераторы.

**Понадобится:** лабораторные 3 и 4. Упражнения делайте в папке `sandbox-05`
с `"type": "module"` в `package.json`. В примерах встречаются классы
и закрытые поля `#` — коротко о них в [шпаргалке](../js-cheatsheet.md#классы),
подробно в лабораторной 8.

**Примерное время:** 2,5 часа.

## Теория

### Зачем события

Сокет не знает, когда придут данные, а сервер — когда подключится
следующий клиент. Вместо того чтобы постоянно спрашивать «ну что, есть?»,
код **подписывается** на событие, и его обработчик вызывают, когда событие
случилось. Это шаблон «Наблюдатель» (Observer). Почти всё в Node.js
устроено так: сокеты, серверы, потоки, `readline`, `process`.

### EventEmitter

```js
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();
const handler = (text, from) => console.log(`${from}: ${text}`);

emitter.on('message', handler); // подписаться
emitter.once('message', () => console.log('first message!')); // только один раз
emitter.emit('message', 'hi', 'ann'); // аргументы emit попадают в обработчики
emitter.off('message', handler); // отписаться можно только той же самой функцией
```

- `emit` вызывает обработчики **синхронно**, по порядку подписки,
  и возвращается только после того, как отработали все.
- `emit` возвращает `true`, если обработчики были, и `false`, если нет.
- Анонимную стрелку `on('x', () => ...)` потом не отписать:
  чтобы вызвать `off`, сохраните функцию в переменную.
- `emitter.listenerCount('message')` — сколько обработчиков подписано на событие.

### Свой класс с событиями

```js
import { EventEmitter } from 'node:events';
import readline from 'node:readline';

export class TerminalUI extends EventEmitter {
  #rl; // закрытое поле: снаружи класса его не видно

  constructor() {
    super(); // обязательно и первой строкой: инициализирует сам EventEmitter
    this.#rl = readline.createInterface({ input: process.stdin, output: process.stdout });
    this.#rl.on('line', (line) => this.emit('line', line)); // пересказываем событие readline
  }
}

const ui = new TerminalUI();
ui.on('line', (text) => console.log(`you typed ${text}`));
```

### `this` в обработчиках

Внутри метода `this` — объект, у которого метод вызвали: в `ui.start()`
это `ui`. Но обработчик события или таймера вызываете не вы, а кто-то
другой, и `this` в нём зависит от того, **как** написана функция:

```js
class Ticker extends EventEmitter {
  start() {
    // Стрелочная функция берёт this снаружи — из метода start. Правильно:
    setInterval(() => this.emit('tick'), 100);

    // Обычная function получает свой this (здесь — объект таймера). Ошибка:
    // setInterval(function () { this.emit('tick'); }, 100);
    // → TypeError: this.emit is not a function
  }
}
```

Та же ловушка — передать метод без вызова: `socket.on('data', this.#handleData)`.
Метод «отрывается» от объекта, и внутри него `this` уже не ваш класс.
Правило простое: **колбэки внутри класса пишите стрелочными функциями**:
`socket.on('data', (chunk) => this.#handleData(chunk))`.

Так класс сообщает о том, что случилось, но **не знает**, кто и что
будет с этим делать. `TerminalUI` говорит «пользователь ввёл строку»,
а решает, отправить её на сервер или выполнить команду, уже `ChatClient`.

Список событий класса стоит описать в комментарии рядом с ним: это часть
его интерфейса, такая же, как методы.

### Особое событие `error`

Если вызвать `emit('error', err)`, а обработчика `error` нет,
EventEmitter **выбросит** `err` как исключение. Никто его не поймает,
и процесс упадёт. Поэтому у каждого сокета обязательно должен быть
обработчик `error`. Иначе разрыв связи у одного клиента
(`ECONNRESET`) уронит весь сервер.

### Исключение внутри обработчика

Обработчик — обычная функция, и он может выбросить исключение. Что будет
дальше, зависит от того, **кто** вызвал `emit`:

- если `emit` вызвали вы сами, исключение вылетит из `emit()` прямо
  в ваш код, и его можно поймать `try/catch` вокруг `emit`;
- если событие испустил сокет или таймер (то есть позже, из цикла событий),
  вокруг `emit` нет вашего кода. Исключение никто не поймает, и процесс упадёт.
  `try/catch` вокруг `socket.on(...)` здесь **не поможет**: он закончил работу
  в момент подписки, задолго до события.

Поэтому граница ошибок ставится **внутри** обработчика:

```js
connection.on('message', (text) => {
  try {
    handleMessage(text);
  } catch (error) {
    logger.error(error.stack); // один кривой запрос не роняет весь сервер
  }
});
```

### События как промисы: `events.once`

```js
import { once } from 'node:events';

server.listen(port);
await once(server, 'listening'); // ждём событие
```

`once` возвращает промис с массивом аргументов события. Если раньше
нужного события придёт `error`, промис **отклонится** с этой ошибкой.
Это ровно то, что нужно для «запусти сервер или скажи, почему не вышло».

### События как поток: `events.on`

```js
import { on } from 'node:events';

for await (const [text] of on(connection, 'message', { close: ['close'] })) {
  console.log(text);
}
// сюда попадём, когда случится 'close'
```

`on` складывает события в очередь, поэтому ни одно не теряется, даже
если код пока занят другим. Опция `close` задаёт события, на которых
цикл закончится.

### Асинхронный итератор

`on(...)` возвращает **асинхронный итератор** — объект с методом `next()`,
который возвращает промис следующего значения:

```js
const messages = on(connection, 'message', { close: ['close'] });

const { value, done } = await messages.next(); // ждём одно событие
// value — массив аргументов события, например ['hello']
// done === true, если поток закончился (случилось 'close')
```

`for await (const x of iterable)` — то же самое, но в цикле: он вызывает
`next()`, пока не получит `done: true`. Удобно запомнить так:

- `for await` — «обработать всё по порядку»;
- `await iterator.next()` — «дай мне одно следующее», как в тестах:
  отправили запрос и ждём ровно один ответ.

Ещё три правила:

- очередь копит только события, случившиеся **после** вызова `on(...)`.
  Создайте итератор до того, как управление вернётся в цикл событий
  (до первого `await`) и до любого синхронного `emit`. Тогда события,
  которые придут из сети или от таймера, точно попадут в очередь;
- `break` внутри `for await` отписывает итератор от событий. Если вы
  читали через `next()` и больше не нужно, отпишитесь сами:
  `await iterator.return()`;
- если источник испустит `error`, цикл (или `next()`) выбросит эту ошибку.

## Упражнения

Решения лежат в [solution/](solution/).

### Упражнение 1. Тикер

Напишите класс `Ticker extends EventEmitter` с двумя методами:

- `start({ intervalMs = 100, count = 3 } = {})` — запускает `setInterval`.
  На каждом срабатывании испускает `tick` с номером тика (с 1). После тика
  номер `count` останавливается и испускает `done`;
- `stop()` — `clearInterval`. Идентификатор таймера храните в закрытом поле `#timer`.

Подпишитесь на `tick` через `on`, ещё раз через `once` и на `done`,
затем вызовите `start({ count: 3 })`.

**Проверка:**

```
tick 1
first tick only
tick 2
tick 3
done
```

### Упражнение 2. Синхронность `emit`

Подпишите на одно событие два обработчика и выведите строку до `emit`
и после него. В каком порядке появились строки? Что вернул `emit` для
события без подписчиков? Подпишите третий обработчик, отпишите его
и проверьте `listenerCount`.

### Упражнение 3. Событие `error`

Испустите `error` без обработчика и посмотрите на вывод и код выхода.
Затем добавьте обработчик и убедитесь, что программа продолжает работу
(`still alive`).

### Упражнение 4. `once` и ошибка

Добавьте в `start` параметр `failAt` (по умолчанию `null`): на тике с этим
номером тикер вместо `tick` останавливается и испускает
`error` с `new Error('Tick N failed')`. Дождитесь `done` через `await once(...)`:

- у тикера без ошибки — получаем `done`;
- у тикера с `failAt: 2` — промис отклоняется, ловим ошибку в `try/catch`.

### Упражнение 5. `on` и `for await`

Соберите номера всех тиков в массив циклом `for await` по `on(ticker, 'tick', { close: ['done'] })`.
Цикл должен закончиться сам, на событии `done`. Ожидаемо: `on: collected ticks 1, 2, 3, 4`
для `count: 4`. Затем получите первые два тика без цикла, двумя вызовами
`await iterator.next()`.

### Упражнение 6. Исключение в обработчике

Подпишите на событие `message` обработчик, который выбрасывает исключение
на тексте `'bad'`. Попробуйте три варианта и объясните результат:

1. `emit('message', 'bad')` внутри `try/catch` — ошибка поймана;
2. `setImmediate(() => emitter.emit('message', 'bad'))` внутри того же
   `try/catch` — процесс падает;
3. `try/catch` внутри обработчика — ошибка поймана, процесс жив.

Решение — [solution/handler-throw.js](solution/handler-throw.js).

## Шаг проекта

Логику чата хочется писать и проверять до того, как появится сеть.
Для этого сделаем «соединение в памяти» — двойник настоящего соединения
для тестов.

Создайте в проекте `chat/` файл `test/fake-connection.js`. В нём будет класс
`FakeConnection extends EventEmitter` (один конец провода) и функция
`createConnectionPair()`, которая создаёт два конца, связывает их
и возвращает массив `[clientSide, serverSide]`.

Правила, на которые опираются тесты в лабораторных 8 и 15:

1. У каждого конца есть поле `remoteAddress` — любая строка для логов
   (например, `'fake-client'` и `'server'`).
2. `send(text)` на одном конце испускает `message` с этим `text` на другом,
   **асинхронно** — через `setImmediate`, как настоящая сеть.
3. Сообщения приходят в том порядке, в котором их отправили.
4. `close()` на любом конце закрывает **оба**: каждый испускает `close`
   ровно один раз. Повторный `close()` ничего не делает.
5. Всё, что отправили **до** `close()`, приходит раньше события `close`.
6. `send` после закрытия молча ничего не делает.

Подсказка: заведите поля `peer` (другой конец) и `isClosed`. Порядок из
правила 5 получится сам, если и доставку, и `close` делать через `setImmediate`:
колбэки `setImmediate` выполняются в том порядке, в котором их поставили
(лабораторная 4).

**Почему не прямой `emit`.** Если `send` сразу вызовет `peer.emit('message')`,
обработчик получателя выполнится **внутри** `send` отправителя, пока тот
не закончил свой код. Эхо-ответ придёт раньше, чем отправитель допишет
следующую строку, а два собеседника, отвечающие друг другу, уйдут
в бесконечную рекурсию и переполнят стек. Код, который работает с таким
«синхронным проводом», сломается на настоящей сети, где ответ всегда
приходит позже. `setImmediate` откладывает доставку до следующего витка
цикла событий — как настоящая сеть.

**Проверка:** на `serverSide` эхо-обработчик, на `clientSide` — печать
полученного. Отправьте два сообщения и закройте соединение **после** ответов
(например, через `setTimeout(..., 10)`):

```
client got "echo: hello"
client got "echo: world"
client side: closed
server side: closed
```

Если закрыть сразу после двух `send`, эхо-ответов не будет: сервер ответит,
когда соединение уже закрыто, и по правилу 6 ответ пропадёт. Это правильное
поведение. Готовый вариант — [solution/fake-connection.js](solution/fake-connection.js)
и [solution/fake-demo.js](solution/fake-demo.js).

Именно такой интерфейс соединения будет у настоящего транспорта
в лабораторной 13, а пока пара пригодится в лабораторной 8.

## Контрольные вопросы

1. Обработчики вызываются синхронно или асинхронно? Что из этого следует?
2. Почему стрелочную функцию, переданную в `on`, нельзя отписать?
3. Что произойдёт при `emit('error')` без обработчика? Почему это опасно для сервера?
4. Чем `events.once` удобнее, чем `emitter.once` с колбэком?
5. Зачем `events.on` складывает события в очередь? Что вернёт `iterator.next()`?
6. Почему `try/catch` вокруг `socket.on(...)` не ловит исключение из обработчика?
   Где ставить границу ошибок?
7. Почему `FakeConnection.send` доставляет сообщение через `setImmediate`,
   а не прямым вызовом `emit`?
