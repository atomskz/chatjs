# Лабораторная 5. События: EventEmitter

**Цель:** понять событийную модель Node.js — на ней построены сокеты,
серверы, терминал и почти всё остальное. Вы научитесь подписываться
на события и испускать свои, писать классы с событиями, не терять `this`,
правильно обращаться с ошибками в событиях и ждать события через промисы
и `for await`.

с `"type": "module"` в `package.json`. В примерах встречаются классы
и закрытые поля `#` — коротко о них в [шпаргалке](../js-cheatsheet.md#классы),
подробно в лабораторной 8.

**Примерное время:** 4–5 часов, два занятия.

**Как работать:** каждый пример запускайте у себя и сверяйте вывод.
В разминках сначала запишите **свой** ответ, потом запустите код и только

## Занятие 1. EventEmitter и свои события

### 1.1. Зачем события

Вы ждёте посылку. Можно каждые пять минут звонить в службу доставки:
«ну что, привезли?». А можно один раз подписаться на SMS — и вам напишут,
когда посылка приедет. Второй способ проще, и вы свободны, пока ждёте.

В программе так же. Сервер не знает, когда подключится следующий клиент,
а сокет — когда придут данные. Вместо того чтобы постоянно спрашивать
«есть что-нибудь?», код **подписывается** на событие: «когда придут
данные — вызови вот эту функцию». Функцию называют **обработчиком**
(listener), а этот приём — шаблоном «Наблюдатель» (Observer).

```
                  emit('message', 'hi', 'ann')
     источник ─────────────┬────────────────────────┐
  (EventEmitter)           ▼                        ▼
                 обработчик 1('hi', 'ann')   обработчик 2('hi', 'ann')
```

Источник **испускает** (emit) событие с именем и данными, а все
подписанные на это имя обработчики получают данные. Источник не знает,
кто на него подписан и что эти функции будут делать.

### 1.2. Разобранный пример: первый EventEmitter

В Node.js источник событий — это объект класса `EventEmitter`
из модуля `node:events`.

```js
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();
emitter.on('message', (text, from) => console.log(`${from}: ${text}`));
emitter.on('message', (text) => console.log(`length: ${text.length}`));

console.log('before emit');
emitter.emit('message', 'hi', 'ann');
console.log('after emit');
```

```
before emit
ann: hi
length: 2
after emit
```

Что происходит по шагам:

| шаг | код                                    | что делает                                                       |
| --- | -------------------------------------- | ---------------------------------------------------------------- |
| 1   | `emitter.on('message', ...)` ×2        | запоминает два обработчика для имени `message`                   |
| 2   | `console.log('before emit')`           | `before emit`                                                    |
| 3   | `emitter.emit('message', 'hi', 'ann')` | вызывает первый обработчик с `('hi', 'ann')`, затем второй       |
| 4   | `console.log('after emit')`            | `after emit` — только после того, как оба обработчика отработали |

Главное: **`emit` вызывает обработчики синхронно**, прямо сейчас,
по порядку подписки, и возвращается только после них. Это не таймер
и не промис: никакой очереди здесь нет. Аргументы `emit` после имени
события целиком передаются обработчикам.

### 1.3. Подписка, отписка, «один раз»

```js
const handler = (text) => console.log(text);

emitter.on('message', handler); // подписаться (можно много раз и много обработчиков)
emitter.once('message', () => console.log('first!')); // сработает один раз и отпишется сам
emitter.off('message', handler); // отписаться — передать ТУ ЖЕ функцию
emitter.listenerCount('message'); // сколько обработчиков подписано
emitter.emit('message', 'hi'); // true, если обработчики были; false, если нет
```

`off` ищет ровно ту функцию, которую ему передали. Две одинаковые
по тексту стрелочные функции — это **разные** функции. Поэтому если
обработчик может понадобиться отписать, сохраните его в переменную.

Имена событий — обычные строки, и EventEmitter их не проверяет. Опечатка
в `emit('mesage')` не вызовет ошибки: просто никто не подписан на такое
имя, и событие пропадёт молча.

### 1.4. Разобранный пример: свой класс с событиями

Обычно EventEmitter не создают сам по себе, а **наследуют** от него свой
класс. Тогда у объекта есть и свои методы, и `on`/`emit`.

```js
import { EventEmitter } from 'node:events';

// События:
//   'ring' (visitor) — кто-то позвонил в дверь
class Doorbell extends EventEmitter {
  press(visitor) {
    console.log(`${visitor} pressed the button`);
    this.emit('ring', visitor);
  }
}

const bell = new Doorbell();
bell.on('ring', (visitor) => console.log(`owner: opening the door for ${visitor}`));
bell.on('ring', () => console.log('dog: woof!'));
bell.press('postman');
```

```
postman pressed the button
owner: opening the door for postman
dog: woof!
```

- `extends EventEmitter` — `Doorbell` умеет всё, что EventEmitter, плюс свой метод `press`.
- Внутри методов класса событие испускают через `this.emit(...)`.
- Звонок **не знает**, кто на него подписан: хозяин, собака или никто.
  Он сообщает «позвонили», а что с этим делать — решают подписчики.
- Список событий класса описывают в комментарии над ним: это часть
  интерфейса класса, такая же, как методы.

Если у класса есть свой конструктор, первой строкой в нём должен стоять
`super()`: он подготавливает ту часть объекта, которая от EventEmitter.

```js
class Bell extends EventEmitter {
  constructor(name) {
    super(); // сначала родитель
    this.name = name; // потом свои поля
  }
}
```

Если обратиться к `this` до `super()`, будет
`ReferenceError: Must call super constructor in derived class before accessing 'this'`.

Так устроен и интерфейс терминала в проекте (лабораторная 9): он
«пересказывает» событие `line` модуля `readline` своим событием `line`,
а что делать с введённой строкой, решает уже логика чата.

### 1.5. `this` в обработчиках

**Зачем об этом знать.** Внутри класса почти всегда хочется в обработчике
события или таймера вызвать свой метод или испустить своё событие через
`this`. И здесь новички чаще всего получают странную ошибку.

**Разобранный пример ошибки.**

```js
class Ticker extends EventEmitter {
  start() {
    setTimeout(function () {
      this.emit('tick');
    }, 10);
  }
}
new Ticker().start();
```

```
      this.emit('tick');
           ^
TypeError: this.emit is not a function
```

Почему: `this` внутри функции зависит от того, **как её вызвали**. В методе
`start` вы вызвали `ticker.start()`, и `this` — это `ticker`. Но функцию
внутри `setTimeout` вызывает уже не вы, а таймер, и у обычной `function`
`this` в этот момент — не ваш объект.

**Исправление** — стрелочная функция. У неё нет своего `this`: она берёт
`this` из того места, где написана, то есть из метода `start`:

```js
class Ticker extends EventEmitter {
  start() {
    setTimeout(() => this.emit('tick'), 10); // this — наш Ticker
  }
}
```

Та же ловушка — передать метод, не вызывая его: `socket.on('data', this.handleData)`.
Метод «отрывается» от объекта, и внутри него `this` уже другой. Правило:
**колбэки внутри класса пишите стрелочными функциями** —
`socket.on('data', (chunk) => this.handleData(chunk))`.

## Занятие 2. Ошибки и ожидание событий

### 2.1. Особое событие `error`

**Зачем.** У сокета, сервера, файла что-то может пойти не так: оборвалась
связь, порт занят. Об этом они сообщают событием с особым именем `error`.

У него одно отличие от остальных событий:

```
emit('error', err)
   ├── есть обработчик 'error' → он получает err, программа работает дальше
   └── нет обработчика         → EventEmitter выбрасывает err как исключение
                                  → его никто не поймал → процесс падает
```

```js
const emitter = new EventEmitter();
emitter.on('error', (error) => console.log(`handled: ${error.message}`));
emitter.emit('error', new Error('socket hang up')); // handled: socket hang up
```

Без строки с `on('error')` программа упадёт со стеком и кодом выхода 1.
Поэтому **у каждого сокета обязательно должен быть обработчик `error`**.
Иначе разрыв связи у одного клиента (`ECONNRESET`) уронит весь сервер
со всеми остальными клиентами.

### 2.2. Исключение внутри обработчика

**Зачем.** Обработчик — обычная функция, и в нём может быть ошибка: кривые
данные от клиента или баг. Важно понять, где её можно поймать.

**Разобранный пример.** Обработчик выбрасывает исключение на тексте `'bad'`.

**Вариант 1. `emit` вызываем сами, внутри `try`:**

```js
const e = new EventEmitter();
e.on('save', (name) => {
  if (!name) throw new Error('name is required');
  console.log(`saved ${name}`);
});

try {
  e.emit('save', ''); // обработчик выполняется ПРЯМО ЗДЕСЬ, внутри try
} catch (error) {
  console.log(`caught: ${error.message}`); // caught: name is required
}
e.emit('save', 'notes'); // saved notes
```

`emit` синхронный (1.2), поэтому исключение из обработчика вылетает
из `emit` прямо в ваш `try`.

**Вариант 2. Событие приходит позже — от сети, таймера, файла.**
Тогда вокруг `emit` нет вашего кода: его вызывает цикл событий.
`try/catch`, который вы поставили вокруг `socket.on(...)`, закончил
работу в момент подписки — задолго до события. Исключение никто не поймает,
и процесс упадёт.

```
ваш код:   try { socket.on('data', handler) } catch {...}   ← выполнился и закончился
               ...проходит время...
сеть:      socket.emit('data', chunk) → handler → throw     ← вокруг нет никакого try
```

**Вариант 3 — правильный.** Граница ошибок ставится **внутри** обработчика:

```js
connection.on('message', (text) => {
  try {
    handleMessage(text);
  } catch (error) {
    logger.error(error.stack); // один кривой запрос не роняет весь сервер
  }
});
```

Все три варианта собраны в [solution/handler-throw.js](solution/handler-throw.js):
`node handler-throw.js sync`, `later` и `inside`.

### 2.3. Ждём одно событие: `events.once`

**Зачем.** Часто нужно не «реагировать на каждое событие», а «подождать,
пока случится вот это одно». Например, пока сервер начнёт слушать порт.
Для этого есть функция `once` из `node:events` — она превращает событие
в промис (лабораторная 4).

```js
import { EventEmitter, once } from 'node:events';

const e = new EventEmitter();
const promise = once(e, 'ready'); // подписались и получили промис
e.emit('ready', 'v1', 42);
console.log(await promise); // [ 'v1', 42 ] — массив аргументов события
```

Самое полезное свойство: если **раньше** нужного события придёт `error`,
промис **отклонится** с этой ошибкой.

```js
const e = new EventEmitter();
setTimeout(() => e.emit('error', new Error('boom')), 10);

try {
  await once(e, 'done');
  console.log('done');
} catch (error) {
  console.log(`failed: ${error.message}`); // failed: boom
}
```

Это ровно то, что нужно для «запусти сервер или скажи, почему не вышло»:

```js
server.listen(port);
await once(server, 'listening'); // либо сервер слушает, либо исключение EADDRINUSE
```

Не путайте два `once`: метод `emitter.once(name, fn)` из 1.3 вызывает
функцию один раз, а функция `once(emitter, name)` возвращает промис.

### 2.4. Ждём много событий: `events.on` и `for await`

**Зачем.** Иногда нужно обработать события **по порядку, одно за другим**,
и при этом ждать между ними: «получи сообщение, ответь, получи следующее».
Обработчик `on` для этого неудобен, а вот цикл — удобен.

Функция `on` из `node:events` превращает поток событий в **асинхронный
итератор** — объект, из которого события можно доставать по одному.
Пока вы заняты, новые события не теряются, а складываются в очередь:

```
события:   tick(1)    tick(2)    tick(3)    done
              │          │          │         │
              ▼          ▼          ▼         ▼
очередь:   [ [1] ,     [2] ,      [3] ]    закрыть
              │
for await ────┘ берёт по одному, пока очередь не закрыта
```

```js
import { on } from 'node:events';

for await (const [n] of on(ticker, 'tick', { close: ['done'] })) {
  console.log(`tick ${n}`); // каждое значение — массив аргументов события
}
console.log('all ticks received'); // сюда попадём после события done
```

- `for await (const x of ...)` — цикл, который на каждом шаге ждёт следующее значение.
- `[n]` — деструктуризация: из массива аргументов события берём первый.
- `{ close: ['done'] }` — на каком событии цикл закончится. Без этой опции
  цикл ждал бы новых событий вечно.

**Одно значение за раз — `next()`.** Итератор можно читать и без цикла:

```js
const messages = on(connection, 'message', { close: ['close'] });

const { value, done } = await messages.next(); // ждём одно событие
// value — массив аргументов события, например ['hello']
// done === true, если поток закончился (случилось 'close')
```

Удобно запомнить так: `for await` — «обработать всё по порядку»,
`await iterator.next()` — «дай мне одно следующее». Второй вариант
нужен в тестах: отправили запрос — ждём ровно один ответ.

Три правила:

- очередь копит только события, случившиеся **после** вызова `on(...)`.
  Создавайте итератор до того, как события могут начаться;
- `break` внутри `for await` отписывает итератор от событий. Если вы
  читали через `next()` и больше не нужно, отпишитесь сами:
  `await iterator.return()`;
- если источник испустит `error`, цикл (или `next()`) выбросит эту ошибку.

### Упражнение 2. Тикер

### Упражнение 3. Свой EventEmitter

Чтобы убедиться, что внутри нет никакой магии, напишите класс `MyEmitter`
с методами `on`, `off`, `emit` и `once`. Подсказки:

- храните обработчики в `Map`: имя события → массив функций;
- `emit(name, ...args)` перебирает массив и вызывает каждую функцию с `...args`,
  а возвращает `true`, если обработчики были;
- `off` оставляет в массиве все функции, кроме переданной (`filter`);
- `once` подписывает функцию-обёртку, которая сначала отписывает саму себя,
  а потом вызывает настоящий обработчик.

Проверьте: один и тот же код с `MyEmitter` и с настоящим `EventEmitter`
должен печатать одно и то же. Решение — [solution/my-emitter.js](solution/my-emitter.js)
и [solution/my-emitter-demo.js](solution/my-emitter-demo.js).

### Упражнение 6. `once` и ошибка

Добавьте в `start` параметр `failAt` (по умолчанию `null`): на тике с этим
номером тикер вместо `tick` останавливается и испускает
`error` с `new Error('Tick N failed')`. Дождитесь `done` через `await once(...)`:

- у тикера без ошибки — получаем `done`;
- у тикера с `failAt: 2` — промис отклоняется, ловим ошибку в `try/catch`.

### Упражнение 7. `on` и `for await`

Соберите номера всех тиков в массив циклом `for await` по `on(ticker, 'tick', { close: ['done'] })`.
Цикл должен закончиться сам, на событии `done`. Ожидаемо: `on: collected ticks 1, 2, 3, 4`
для `count: 4`. Затем получите первые два тика без цикла, двумя вызовами
`await iterator.next()`, и отпишитесь через `iterator.return()`.

### Упражнение 8. Исключение в обработчике

Подпишите на событие `message` обработчик, который выбрасывает исключение
на тексте `'bad'`. Попробуйте три варианта из 2.2 и объясните результат:

1. `emit('message', 'bad')` внутри `try/catch` — ошибка поймана;
2. `setImmediate(() => emitter.emit('message', 'bad'))` внутри того же
   `try/catch` — процесс падает;
3. `try/catch` внутри обработчика — ошибка поймана, процесс жив.

Решение — [solution/handler-throw.js](solution/handler-throw.js).

## Типичные ошибки

| что видите                                                                     | почему                                                             | что делать                                                 |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------- |
| `TypeError: this.emit is not a function`                                       | колбэк написан как `function () {}`, `this` потерян                | стрелочная функция (1.5)                                   |
| `Cannot read private member ... from an object whose class did not declare it` | метод передан без вызова: `on('x', this.#handle)`                  | `on('x', (data) => this.#handle(data))`                    |
| `ReferenceError: Must call super constructor ...`                              | в конструкторе нет `super()` или он стоит после `this`             | `super()` первой строкой конструктора                      |
| обработчик не вызывается                                                       | опечатка в имени события или подписались после `emit`              | сверить имена; подписываться до того, как событие случится |
| обработчик срабатывает дважды                                                  | подписались два раза (например, в функции, которую вызвали дважды) | подписываться один раз; проверить `listenerCount`          |
| `off` не отписывает                                                            | передана другая функция, пусть и с тем же текстом                  | сохранить обработчик в переменную                          |
| процесс упал, в выводе `Emitted 'error' event` или `Unhandled error`           | испущен `error`, а обработчика нет                                 | `on('error', ...)` у каждого сокета и сервера              |
| исключение в обработчике сокета уронило весь сервер                            | `try/catch` стоит снаружи, вокруг подписки                         | `try/catch` внутри обработчика (2.2)                       |
| `MaxListenersExceededWarning: Possible EventEmitter memory leak`               | больше 10 обработчиков на одно событие — обычно подписка в цикле   | найти, где подписка повторяется, и вынести её              |
| `for await` никогда не заканчивается                                           | не указан `close` или событие закрытия называется иначе            | `on(emitter, 'x', { close: ['имя-события'] })`             |
| `for await` пропустил первые события                                           | итератор создан после того, как они случились                      | вызвать `on(...)` раньше                                   |

## Шаг проекта

Логику чата хочется писать и проверять до того, как появится сеть.
Для этого сделаем «соединение в памяти» — двойник настоящего соединения
для тестов.

Создайте в проекте `chat/` файл `test/fake-connection.js`. В нём будет класс
`FakeConnection extends EventEmitter` (один конец провода) и функция
`createConnectionPair()`, которая создаёт два конца, связывает их
и возвращает массив `[clientSide, serverSide]`.

Правила, на которые опираются тесты в лабораторных 8 и 15:

1. У каждого конца есть поле `remoteAddress` — любая строка для логов
   (например, `'fake-client'` и `'server'`).
2. `send(text)` на одном конце испускает `message` с этим `text` на другом,
   **асинхронно** — через `setImmediate`, как настоящая сеть.
3. Сообщения приходят в том порядке, в котором их отправили.
4. `close()` на любом конце закрывает **оба**: каждый испускает `close`
   ровно один раз. Повторный `close()` ничего не делает.
5. Всё, что отправили **до** `close()`, приходит раньше события `close`.
6. `send` после закрытия молча ничего не делает.

Каркас, с которого можно начать:

```js
import { EventEmitter } from 'node:events';

class FakeConnection extends EventEmitter {
  peer = null; // другой конец провода
  isClosed = false;

  constructor(remoteAddress) {
    super();
    this.remoteAddress = remoteAddress;
  }

  send(text) {
    // если закрыто — ничего не делать;
    // иначе через setImmediate испустить 'message' с text на this.peer
  }

  close() {
    // если уже закрыто — ничего не делать;
    // пометить закрытыми оба конца;
    // через setImmediate испустить 'close' на каждом из них
  }
}

export function createConnectionPair() {
  // создать два конца, записать каждому peer другого, вернуть [client, server]
}
```

Порядок из правила 5 получится сам, если и доставку, и `close` делать
через `setImmediate`: колбэки `setImmediate` выполняются в том порядке,
в котором их поставили (лабораторная 4).

**Почему не прямой `emit`.** Если `send` сразу вызовет `peer.emit('message')`,
обработчик получателя выполнится **внутри** `send` отправителя, пока тот
не закончил свой код (1.2: `emit` синхронный). Эхо-ответ придёт раньше,
чем отправитель допишет следующую строку, а два собеседника, отвечающие
друг другу, уйдут в бесконечную рекурсию и переполнят стек. Код, который
работает с таким «синхронным проводом», сломается на настоящей сети,
где ответ всегда приходит позже. `setImmediate` откладывает доставку
до следующего витка цикла событий — как настоящая сеть.

**Проверка:** на `serverSide` эхо-обработчик, на `clientSide` — печать
полученного. Отправьте два сообщения и закройте соединение **после** ответов
(например, через `setTimeout(..., 10)`):

```
client got "echo: hello"
client got "echo: world"
client side: closed
server side: closed
```

Если закрыть сразу после двух `send`, эхо-ответов не будет: сервер ответит,
когда соединение уже закрыто, и по правилу 6 ответ пропадёт. Это правильное
поведение. Готовый вариант — [solution/fake-connection.js](solution/fake-connection.js)
и [solution/fake-demo.js](solution/fake-demo.js).

Именно такой интерфейс соединения будет у настоящего транспорта
в лабораторной 13, а пока пара пригодится в лабораторной 8.
