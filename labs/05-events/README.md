# Лабораторная 5. События: EventEmitter

**Цель:** освоить событийную модель Node.js: подписываться на события,
создавать свои классы-источники событий, правильно обращаться с событием
`error` и превращать события в промисы и асинхронные итераторы.

**Примерное время:** 2 часа.

## Теория

### Зачем события

Сокет не знает, когда придут данные, а сервер — когда подключится
следующий клиент. Вместо того чтобы постоянно спрашивать «ну что, есть?»,
код **подписывается** на событие, и его обработчик вызывают, когда событие
случилось. Это шаблон «Наблюдатель» (Observer). Почти всё в Node.js
устроено так: сокеты, серверы, потоки, `readline`, `process`.

### EventEmitter

```js
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();
emitter.on('message', (text, from) => console.log(`${from}: ${text}`));
emitter.once('message', () => console.log('first message!')); // только один раз
emitter.emit('message', 'hi', 'ann'); // аргументы emit попадают в обработчики
emitter.off('message', handler); // отписка той же самой функцией
```

- `emit` вызывает обработчики **синхронно**, по порядку подписки,
  и возвращается только после того, как отработали все.
- `emit` возвращает `true`, если обработчики были, и `false`, если нет.
- Анонимную стрелку `on('x', () => ...)` потом не отписать:
  чтобы вызвать `off`, сохраните функцию в переменную.

### Свой класс с событиями

```js
export class TerminalUI extends EventEmitter {
  constructor() {
    super(); // обязательно: инициализирует сам EventEmitter
    this.#rl.on('line', (line) => this.emit('line', line));
  }
}
```

Так класс сообщает о том, что случилось, но **не знает**, кто и что
будет с этим делать. `TerminalUI` говорит «пользователь ввёл строку»,
а решает, отправить её на сервер или выполнить команду, уже `ChatClient`.

Список событий класса стоит описать в комментарии рядом с ним: это часть
его интерфейса, такая же, как методы.

### Особое событие `error`

Если вызвать `emit('error', err)`, а обработчика `error` нет,
EventEmitter **выбросит** `err` как исключение. Никто его не поймает,
и процесс упадёт. Поэтому у каждого сокета обязательно должен быть
обработчик `error`. Иначе разрыв связи у одного клиента
(`ECONNRESET`) уронит весь сервер.

### События как промисы: `events.once`

```js
import { once } from 'node:events';

server.listen(port);
await once(server, 'listening'); // ждём событие
```

`once` возвращает промис с массивом аргументов события. Если раньше
нужного события придёт `error`, промис **отклонится** с этой ошибкой.
Это ровно то, что нужно для «запусти сервер или скажи, почему не вышло».

### События как поток: `events.on`

```js
import { on } from 'node:events';

for await (const [text] of on(connection, 'message', { close: ['close'] })) {
  console.log(text);
}
// сюда попадём, когда случится 'close'
```

`on` складывает события в очередь, поэтому ни одно не теряется, даже
если код пока занят другим. Опция `close` задаёт события, на которых
цикл закончится.

## Упражнения

Решения лежат в [solution/](solution/).

### Упражнение 1. Тикер

Напишите класс `Ticker extends EventEmitter` с методами `start({ intervalMs, count })`
и `stop()`. Он испускает `tick` с номером тика (с 1), а после последнего —
`done`. Подпишитесь на `tick` через `on`, ещё раз через `once` и на `done`.

**Проверка:**

```
tick 1
first tick only
tick 2
tick 3
done
```

### Упражнение 2. Синхронность `emit`

Подпишите на одно событие два обработчика и выведите строку до `emit`
и после него. В каком порядке появились строки? Что вернул `emit` для
события без подписчиков? Подпишите третий обработчик, отпишите его
и проверьте `listenerCount`.

### Упражнение 3. Событие `error`

Испустите `error` без обработчика и посмотрите на вывод и код выхода.
Затем добавьте обработчик и убедитесь, что программа продолжает работу
(`still alive`).

### Упражнение 4. `once` и ошибка

Добавьте в `Ticker` параметр `failAt`: на этом тике тикер останавливается
и испускает `error`. Дождитесь `done` через `await once(...)`:

- у тикера без ошибки — получаем `done`;
- у тикера с `failAt: 2` — промис отклоняется, ловим ошибку в `try/catch`.

### Упражнение 5. `on` и `for await`

Соберите номера всех тиков в массив циклом `for await` по `on(ticker, 'tick', { close: ['done'] })`.
Цикл должен закончиться сам, на событии `done`.

## Шаг проекта

Логику чата хочется писать и проверять до того, как появится сеть.
Для этого сделаем «соединение в памяти» — двойник настоящего соединения
для тестов.

Создайте `test/fake-connection.js` с функцией `createConnectionPair()`.
Она возвращает пару `[clientSide, serverSide]` — два конца одного «провода»:

- у каждого конца есть `remoteAddress`, `send(text)` и `close()`, и каждый
  испускает `message` (text) и `close`;
- `send` на одном конце вызывает `message` на другом **асинхронно**
  (`setImmediate`), как настоящая сеть;
- `close` на любом конце закрывает оба. Всё, что отправили до `close`,
  приходит раньше события `close`.

Проверьте: эхо-обработчик на `serverSide` отвечает на два сообщения,
затем `close` вызывает событие `close` на обоих концах.

Именно такой интерфейс соединения будет у настоящего транспорта
в лабораторной 13, а пока пара пригодится в лабораторной 8.

## Контрольные вопросы

1. Обработчики вызываются синхронно или асинхронно? Что из этого следует?
2. Почему стрелочную функцию, переданную в `on`, нельзя отписать?
3. Что произойдёт при `emit('error')` без обработчика? Почему это опасно для сервера?
4. Чем `events.once` удобнее, чем `emitter.once` с колбэком?
5. Зачем `events.on` складывает события в очередь?
6. Почему `FakeConnection.send` доставляет сообщение через `setImmediate`,
