# Лабораторная 11. Поток байтов и фрейминг

**Цель:** своими глазами увидеть, что TCP передаёт поток байтов, а не
сообщения: сообщения склеиваются и разрываются. Научиться работать
с `Buffer` и UTF-8 и самому размечать границы сообщений — разделителем
(NDJSON) и префиксом длины.

**Понадобится:** лабораторная 10.

**Понадобится:** лабораторные 7 и 10. Упражнения делайте в папке `sandbox-11`
с `"type": "module"`.

**Примерное время:** 2,5 часа.

## Теория

### `Buffer` — байты

Сеть и файлы передают байты. В Node.js последовательность байтов — это `Buffer`:

```js
const bytes = Buffer.from('Привет', 'utf8'); // строка → байты
bytes.length; // 12: кириллическая буква в UTF-8 занимает 2 байта
bytes.toString('utf8'); // байты → строка
Buffer.byteLength('😀'); // 4
bytes.subarray(0, 3); // кусок буфера (без копирования)
Buffer.concat([a, b]); // склеить буферы
```

Символ в UTF-8 занимает от 1 до 4 байт: латиница — 1, кириллица — 2,
эмодзи — 4. Если разрезать буфер посередине символа и декодировать
половинки по отдельности, получится `П�` + `�ивет` — символ-заменитель
вместо буквы.

`StringDecoder` из `node:string_decoder` помнит неполный символ из
прошлого куска и отдаёт его, когда придёт продолжение:

```js
const decoder = new StringDecoder('utf8');
decoder.write(firstHalf); // 'П'
decoder.write(secondHalf); // 'ривет' — «р» собралась из двух кусков
```

### Нет границ сообщений

TCP гарантирует одно: байты придут в том же порядке, в каком их отправили.
Как они разобьются на события `data`, не гарантирует никто:

- **склейка** — три `write` подряд могут прийти одним `data`. Отправитель
  копит мелкие куски (алгоритм Нейгла), а получатель забирает всё,
  что успело накопиться;
- **разрыв** — одно большое сообщение приходит несколькими `data`
  (обычно по 64 КБ), и граница может пройти где угодно, даже посередине
  UTF-8 символа.

Локально на быстром компьютере склейка и разрыв случаются редко. Программа,
которая на них не рассчитана, работает «у меня на машине» и ломается в
настоящей сети. Поэтому получатель должен **сам** искать, где кончается
одно сообщение и начинается другое. Это называется **фрейминг**.

### Способы фрейминга

| способ               | как                                     | пример                       |
| -------------------- | --------------------------------------- | ---------------------------- |
| разделитель          | сообщение заканчивается символом `\n`   | NDJSON, HTTP-заголовки       |
| префикс длины        | 4 байта длины, затем ровно столько байт | многие бинарные протоколы    |
| фиксированный размер | каждое сообщение ровно N байт           | редко, для простых устройств |

**NDJSON** (newline-delimited JSON) — одна строка JSON на сообщение.
Работает, потому что `JSON.stringify` никогда не выдаёт перевод строки
(внутри значений он записывается как `\n`, два символа).

### Как резать поток по `\n`

```
буфер: ''
data:  '{"a":1}\n{"b'      → строки: ['{"a":1}'],  остаток '{"b'
data:  '":2}\n'            → строки: ['{"b":2}'],  остаток ''
```

1. Декодировать кусок через `StringDecoder` и добавить к буферу.
2. Разрезать буфер по `\n`. Все части, кроме последней, — готовые строки.
3. Последняя часть — начало следующего, ещё не полного сообщения:
   её оставить в буфере.

Две детали:

- **защита памяти.** Если собеседник шлёт байты без `\n`, буфер растёт
  бесконечно. Задайте предел длины строки и при превышении обрывайте соединение;
- **`\r\n`.** `telnet` и `nc` в Windows завершают строки так. Уберите `\r`
  в конце строки.

## Упражнения

Решения лежат в [solution/](solution/). Решение упражнения 3 — это файлы
эталона [transport/line-splitter.js](../../transport/line-splitter.js)
и [test/line-splitter.test.js](../../test/line-splitter.test.js).

### Упражнение 1. Байты и символы

Для строки `'Привет, 😀'` выведите `length`, число байт и сами байты
в шестнадцатеричном виде. Разрежьте буфер после третьего байта
и декодируйте половинки сначала по отдельности, а потом через `StringDecoder`.

### Упражнение 2. Склейка и разрыв

Напишите программу, в которой сервер печатает каждое событие `data`,
а клиент:

1. делает три `write` подряд с разными JSON-строками;
2. через 100 мс отправляет одну строку длиной 1 МБ.

Сколько событий `data` получил сервер в каждом случае? Посмотрите
на эхо-сервер и сервер рассылки из лабораторной 10: что с ними будет,
если клиент пришлёт два сообщения одним куском?

### Упражнение 3. `LineSplitter`

Напишите класс `LineSplitter` с методом `push(chunk)`. Метод принимает
`Buffer` и возвращает массив строк, которые в этом куске завершились.
Неполный хвост остаётся внутри до следующего вызова. Обязательные случаи
для тестов:

- два сообщения в одном куске;
- одно сообщение в трёх кусках;
- кириллица и эмодзи, разрезанные посередине символа (режьте `Buffer`
  по байтам, а не строку!);
- `\r\n` в конце строки;
- пустые строки пропускаются;
- строка без `\n` длиннее `maxLineLength` — исключение.

### Упражнение 4 (бонус). Префикс длины

Напишите `encodeFrame(text)`: 4 байта длины (`writeUInt32BE`), затем байты
текста. И класс `FrameDecoder` с `push(chunk)`, который возвращает
готовые кадры. Проверьте склейку, разрыв по одному байту, текст
с `\n` внутри и отказ от слишком большого кадра. Сравните оба подхода:
что удобнее отлаживать через `nc`, что быстрее разбирать, какой способ
может передавать двоичные данные?
