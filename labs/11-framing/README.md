# Лабораторная 11. Поток байтов и фрейминг

**Цель:** своими глазами увидеть, что TCP передаёт поток байтов, а не
сообщения: сообщения склеиваются и разрываются. Научиться работать
с `Buffer` и UTF-8 и самому размечать границы сообщений — разделителем
(NDJSON) и префиксом длины.

**Понадобится:** лабораторные 7 и 10. Упражнения делайте в папке `sandbox-11`
с `"type": "module"`.

**Примерное время:** 4 часа, два занятия.

**Как работать:** каждый пример запускайте у себя и сверяйте вывод.
В разминках сначала запишите **свой** ответ, потом проверьте и только
потом смотрите [answers.md](answers.md).

## Занятие 1. Байты и поток

### 1.1. Зачем

В лабораторной 10 эхо-сервер отвечал `echo: <то, что прислали>` на каждое
событие `data`. Но если отправить ему две строки сразу —
`printf 'a\nb\n' | node nc.js localhost 5000`, — он ответит **один** раз:
`echo: a` и `b` пришли одним куском. Для чата это беда: сервер ждёт одно
сообщение JSON, а получает два склеенных или половину одного.

**Аналогия: шланг, а не посылки.** Почта доставляет посылки: что
упаковали одной коробкой, то и придёт одной коробкой. TCP — это шланг:
вы наливаете в него вёдра воды, а с другого конца течёт просто вода.
Сколько было вёдер и где кончалось одно, по струе не понять. Чтобы
получатель мог разделить поток на сообщения, отправитель должен
**разметить** границы. Это называется **фрейминг**.

### 1.2. `Buffer` — байты

Сеть и файлы передают байты. В Node.js последовательность байтов — это `Buffer`:

```js
const bytes = Buffer.from('Привет', 'utf8'); // строка → байты
bytes.length; // 12: кириллическая буква в UTF-8 занимает 2 байта
bytes.toString('utf8'); // байты → строка
Buffer.byteLength('😀'); // 4
bytes.subarray(0, 3); // кусок буфера (без копирования)
Buffer.concat([a, b]); // склеить буферы
bytes.toString('hex'); // 'd09fd180...' — байты в шестнадцатеричном виде
console.log(bytes); // <Buffer d0 9f d1 80 d0 b8 d0 b2 d0 b5 d1 82>
```

Символ в UTF-8 занимает от 1 до 4 байт: латиница — 1, кириллица — 2,
эмодзи — 4:

```
'Привет, 😀'
 П     р     и     в     е     т     ,  ␣  😀
d0 9f d1 80 d0 b8 d0 b2 d0 b5 d1 82 2c 20 f0 9f 98 80
└─2─┘ └─2─┘ └─2─┘ └─2─┘ └─2─┘ └─2─┘ 1  1  └───4────┘   = 18 байт, а text.length — 10
```

### 1.3. Разобранный пример: буква, разрезанная пополам

Разрежем байты `'Привет, 😀'` после третьего байта — посередине буквы «р» —
и декодируем половинки:

```
naive:   "П�" + "�ивет, 😀"
decoder: "П" + "ривет, 😀"
```

- **По отдельности** (`first.toString()` и `second.toString()`): первая
  половина заканчивается первым байтом «р», вторая начинается со второго.
  Ни один из обломков не является буквой, и каждый превращается в `�` —
  символ-заменитель.
- **Через `StringDecoder`** из `node:string_decoder`: он помнит неполный
  символ из прошлого куска и отдаёт его, когда придёт продолжение.

```js
import { StringDecoder } from 'node:string_decoder';

const decoder = new StringDecoder('utf8');
decoder.write(firstHalf); // 'П' — неполная «р» придержана
decoder.write(secondHalf); // 'ривет, 😀' — «р» собралась из двух кусков
```

В сети кусок данных может закончиться где угодно — и посередине буквы тоже.
Поэтому байты из сети в текст переводят через `StringDecoder`, а не
`chunk.toString()` для каждого куска.

### 1.4. Нет границ сообщений

TCP гарантирует одно: байты придут в том же порядке, в каком их отправили.
Как они разобьются на события `data`, не гарантирует никто:

```
отправитель:  write(A)   write(B)   write(C)

получатель может увидеть любое из:
              data(AB)  data(C)
              data(ABC)
              data(A)   data(B)   data(C)
              data(A…)  data(…AB) data(C)     ← A разорвано пополам
```

**Разобранный пример.** [solution/glue-demo.js](solution/glue-demo.js):
клиент делает три `write` подряд, а через 100 мс отправляет одну строку
длиной 1 МБ. Сервер печатает каждое событие `data`:

```
data #1: "{\"type\":\"msg\",\"text\":\"one\"}\n{\"type\":\"msg\",\"text\":\"two\"}\n{\"type\":\"msg\",\"text\":\"three\"}\n"
data #18: "\n"
total: 1048663 bytes in 18 'data' events
```

- **Склейка:** три сообщения пришли **одним** событием `data`.
- **Разрыв:** одна строка в 1 МБ пришла **семнадцатью** кусками примерно
  по 64 КБ, а последний перевод строки — восемнадцатым.

Если в обработчике `data` сразу сделать `JSON.parse(chunk)`, будет так:

| что пришло в `data`          | `JSON.parse`                                                   |
| ---------------------------- | -------------------------------------------------------------- |
| два сообщения сразу          | `Unexpected non-whitespace character after JSON at position 8` |
| половина сообщения           | `Unterminated string in JSON at position 17`                   |
| пустой кусок или только `\n` | `Unexpected end of JSON input`                                 |

Насколько часто это случается, зависит от того, как идут данные:

- `write`, сделанные подряд без паузы, склеиваются почти всегда, даже на
  одном компьютере: получатель читает всё, что успело накопиться;
- сообщения, отправленные с паузой (как реплики в чате), локально обычно
  приходят по одному, и маленькое сообщение локально почти никогда не рвётся.
  В настоящей сети данные идут пакетами примерно по 1500 байт, бывают
  задержки и повторные отправки потерянных пакетов, и склейка с разрывом
  там случаются в любой момент.

Программа, которая на это не рассчитана, работает «у меня на машине»
и ломается в настоящей сети. Поэтому получатель должен **сам** искать,
где кончается одно сообщение и начинается другое.

## Занятие 2. Фрейминг

### 2.1. Способы фрейминга

| способ               | как                                     | пример                       |
| -------------------- | --------------------------------------- | ---------------------------- |
| разделитель          | сообщение заканчивается символом `\n`   | NDJSON, HTTP-заголовки       |
| префикс длины        | 4 байта длины, затем ровно столько байт | многие бинарные протоколы    |
| фиксированный размер | каждое сообщение ровно N байт           | редко, для простых устройств |

**NDJSON** (newline-delimited JSON) — одна строка JSON на сообщение.
Работает, потому что `JSON.stringify` никогда не выдаёт перевод строки
(внутри значений он записывается как `\n`, два символа).

Сравнение двух главных способов:

|                                 | разделитель `\n`                       | префикс длины                                    |
| ------------------------------- | -------------------------------------- | ------------------------------------------------ |
| отладка                         | можно набирать и читать руками в `nc`  | нужна программа: длину руками не посчитать       |
| какие данные                    | без `\n` внутри (JSON это гарантирует) | любые, в том числе двоичные и с `\n`             |
| разбор                          | искать `\n` в накопленном тексте       | прочитать 4 байта и ждать ровно N байт           |
| слишком большое сообщение       | заметно, только когда буфер уже вырос  | размер известен сразу — можно отказать до приёма |
| после одного испорченного байта | следующий `\n` восстанавливает границы | длина «съезжает», и поток уже не разобрать       |

### 2.2. Разобранный пример: режем поток по `\n`

Идея: копить пришедший текст в **буфере**, отдавать наружу только полные
строки, а неполный хвост оставлять до следующего куска.

**Версия 1 — наивная:**

```js
let buffer = '';
function push(chunk) {
  buffer += chunk.toString(); // ← здесь спрятана ошибка
  const parts = buffer.split('\n');
  buffer = parts.pop(); // последняя часть — начало следующего сообщения
  return parts;
}
```

Склейку и разрыв по сообщениям она уже обрабатывает. Но если кусок
закончится посередине буквы, `chunk.toString()` испортит её (1.3):

```js
const bytes = Buffer.from('Привет\n');
push(bytes.subarray(0, 1)); // []
push(bytes.subarray(1)); // [ '��ривет' ] — «П» разорвана на два обломка
```

**Версия 2 — правильная** (так устроен
[transport/line-splitter.js](../../transport/line-splitter.js) эталона):

```js
import { StringDecoder } from 'node:string_decoder';

export class LineSplitter {
  #decoder = new StringDecoder('utf8');
  #buffer = '';
  #maxLineLength;

  constructor({ maxLineLength = 64 * 1024 } = {}) {
    this.#maxLineLength = maxLineLength;
  }

  push(chunk) {
    this.#buffer += this.#decoder.write(chunk); // неполный символ придержит декодер
    const parts = this.#buffer.split('\n');
    this.#buffer = parts.pop(); // неполный хвост ждёт следующего куска
    if (this.#buffer.length > this.#maxLineLength) {
      throw new Error(`Line is longer than ${this.#maxLineLength} characters`);
    }
    return parts
      .map((line) => line.replace(/\r$/, '')) // '\r\n' от telnet и nc в Windows
      .filter((line) => line.trim() !== ''); // пустые строки пропускаем
  }
}
```

**Как он работает по шагам:**

| вызов `push(...)` | буфер до | после `split('\n')`  | наружу        | буфер после |
| ----------------- | -------- | -------------------- | ------------- | ----------- |
| `'{"a":1}\n{"b'`  | `''`     | `['{"a":1}', '{"b']` | `['{"a":1}']` | `'{"b'`     |
| `'":2}\n'`        | `'{"b'`  | `['{"b":2}', '']`    | `['{"b":2}']` | `''`        |
| `'\n\n'`          | `''`     | `['', '', '']`       | `[]`          | `''`        |
| `'hi\r\n'`        | `''`     | `['hi\r', '']`       | `['hi']`      | `''`        |

Ещё две детали:

- **защита памяти.** Если собеседник шлёт байты без `\n`, буфер растёт
  бесконечно и съест всю память сервера. Поэтому длина неполной строки
  ограничена, и при превышении `push` выбрасывает исключение — транспорт
  в ответ рвёт соединение (лабораторная 13);
- **`\r\n`.** `telnet` и `nc` в Windows завершают строки так. `\r` в конце
  убирают: иначе `'exit\r' === 'exit'` — `false`.

### 2.3. Префикс длины

Числа тоже можно записывать в буфер байтами — это нужно для префикса длины:

```js
const header = Buffer.alloc(4); // 4 нулевых байта
header.writeUInt32BE(12); // записать число 12 как 4 байта: 00 00 00 0c
header.readUInt32BE(0); // прочитать 4 байта с позиции 0 обратно в число: 12
```

`UInt32` — целое без знака в 32 битах (4 байтах), от 0 до 4 294 967 295.
`BE` (big-endian) — старший байт идёт первым, как цифры в обычной записи
числа. В сетевых протоколах принят именно такой порядок.

```
кадр для 'Привет':   00 00 00 0c   d0 9f d1 80 d0 b8 d0 b2 d0 b5 d1 82
                     └─ длина 12 ┘ └──────────── 12 байт текста ──────────┘
```

Длина — в **байтах**, а не в символах: `Buffer.byteLength(text)`,
а не `text.length` (для `'Привет'` это 12, а не 6).

Разбор: пока в буфере есть хотя бы 4 байта — прочитать длину; если в буфере
уже есть ещё столько байт — отрезать кадр и повторить, иначе ждать
следующего куска. Читать длину раньше, чем пришли 4 байта, нельзя:
`readUInt32BE` выбросит `RangeError: Attempt to access memory outside buffer bounds`.

## Типичные ошибки

| что видите                                                     | почему                                          | что делать                                              |
| -------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------- |
| `Unexpected non-whitespace character after JSON at position N` | два сообщения пришли одним куском               | резать поток по `\n`, а не разбирать каждый `data`      |
| `Unterminated string in JSON` / `Unexpected end of JSON input` | пришла половина сообщения или пустой кусок      | копить хвост в буфере до `\n`; пропускать пустые строки |
| `�` вместо букв, особенно в длинных сообщениях                 | каждый кусок декодирован отдельно               | `StringDecoder`                                         |
| последнее сообщение пропало                                    | хвост буфера выброшен (`buffer = ''`)           | `buffer = parts.pop()`                                  |
| память сервера растёт, пока клиент шлёт данные без `\n`        | нет ограничения длины строки                    | `maxLineLength` и разрыв соединения                     |
| строка `'exit'` не совпадает, хотя на экране `exit`            | клиент прислал `\r\n`                           | убрать `\r` в конце строки                              |
| префикс длины: кадр с кириллицей разбирается неправильно       | длина посчитана в символах (`text.length`)      | `Buffer.byteLength(text)`                               |
| `RangeError: Attempt to access memory outside buffer bounds`   | длину читают, пока в буфере меньше 4 байт       | сначала проверить `buffer.length >= 4`                  |
| локально всё работает, а в настоящей сети сообщения ломаются   | код рассчитан, что один `data` — одно сообщение | фрейминг всегда, даже если локально «и так работает»    |
