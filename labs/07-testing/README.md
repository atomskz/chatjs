# Лабораторная 7. Автотесты: `node:test`

**Цель:** научиться писать автотесты встроенными средствами Node.js:
проверять обычные и асинхронные функции, ожидаемые исключения и события;
готовить и убирать окружение теста; запускать тесты одной командой.

**Примерное время:** 2 часа.

## Теория

### Зачем тесты

Тест — это программа, которая проверяет другую программу. Он запускается
за секунды и проверяет то, что руками пришлось бы перепроверять после
каждой правки. Главная польза тестов — смелость: можно переписать
модуль и через секунду узнать, что ничего не сломалось.

### `node:test` и `node:assert`

В Node.js всё для тестов уже есть, ставить ничего не нужно:

```js
import assert from 'node:assert/strict';
import { describe, test } from 'node:test';
import { parsePort } from '../lib/cli.js';

describe('parsePort', () => {
  test('accepts 5000', () => {
    assert.equal(parsePort('5000'), 5000);
  });
});
```

Тест считается упавшим, если внутри него выброшено исключение.
Проверки `assert` как раз выбрасывают исключение, когда условие не выполнено.

| проверка                            | что проверяет                                |
| ----------------------------------- | -------------------------------------------- |
| `assert.equal(a, b)`                | `a === b`                                    |
| `assert.deepEqual(a, b)`            | объекты или массивы совпадают по содержимому |
| `assert.ok(value)`                  | значение истинно                             |
| `assert.match(text, /re/)`          | строка подходит под регулярное выражение     |
| `assert.throws(fn, expected)`       | `fn()` выбрасывает подходящую ошибку         |
| `await assert.rejects(p, expected)` | промис отклоняется подходящей ошибкой        |

`expected` у `throws` и `rejects` бывает разным:

- класс — `assert.throws(fn, UsageError)`;
- объект с ожидаемыми полями — `{ code: 'ETIMEDOUT' }`;
- регулярное выражение для `message` — `/longer/`;
- функция-проверка, которая возвращает `true`.

Модуль `node:assert/strict` важнее, чем кажется: в нём `equal` сравнивает
через `===`. В нестрогом `node:assert` проверка `assert.equal(1, '1')` проходит.

### Асинхронные тесты

Если функция теста `async`, `node:test` дождётся её промиса:

```js
test('connects', async () => {
  const connection = await connect({ host: '127.0.0.1', port });
  assert.equal(await nextMessage(connection), 'hello');
});
```

Забытый `await` перед `assert.rejects` — частая ошибка: тест закончится
раньше проверки и пройдёт, даже если код сломан.

### Табличные тесты

Однотипные случаи удобно описать массивом и создать тесты в цикле:

```js
for (const input of ['0', '65536', 'abc', '']) {
  test(`rejects "${input}"`, () => {
    assert.throws(() => parsePort(input), UsageError);
  });
}
```

### Подготовка и уборка: хуки

```js
describe('server', () => {
  let server;
  beforeEach(async () => {
    server = await startServer();
  });
  afterEach(async () => {
    await server.stop(); // выполнится, даже если тест упал
  });
});
```

Есть также `before` и `after` (один раз на весь `describe`) и `t.after(fn)`
внутри конкретного теста. Неубранный сервер или таймер — частая причина
того, что тесты «зависают» после последнего теста.

### Фиктивное время

`t.mock.timers.enable({ apis: ['setTimeout'] })` подменяет таймеры,
и `t.mock.timers.tick(60_000)` «перематывает» минуту мгновенно.

### Запуск

```bash
node --test                          # найти и запустить *.test.js и тесты в папке test/
node --test "test/**/*.test.js"      # только файлы по шаблону
node --test --watch                  # перезапускать при изменении файлов
node --test --test-timeout=10000     # упавший по таймауту тест не повесит весь прогон
```

Шаблон в кавычках раскрывает сам Node.js, поэтому команда одинаково
работает в bash и в PowerShell. В `package.json` её кладут в скрипт `test`
и запускают через `npm test`.

### Что тестировать

Тестируйте **поведение через публичный интерфейс**: «на вход `'abc'` —
ошибка `UsageError`», а не «внутри вызывается регулярное выражение».
Тогда тест не придётся переписывать при каждом рефакторинге.

### Упражнение 1. Табличные тесты для `lib/cli.js`

Напишите тесты для `parsePort`: три правильных значения и восемь неправильных
(`'0'`, `'65536'`, `'abc'`, `''`, `' 80'`, `'5.5'`, `'1e3'`, `'-1'`). Для
`requireOption` проверьте и класс ошибки, и её текст.

### Упражнение 2. Тесты протокола

Для своего `protocol.js` из лабораторной 6 проверьте:

- `decode(encode(message))` возвращает то же сообщение, в том числе
  с кириллицей и эмодзи;
- `decode` выбрасывает `ProtocolError` с кодом `BAD_MESSAGE` для `'hello'`,
  `''`, `'null'`, `'42'`, `'[1]'`, `'{"text":"hi"}'` и `'{"type":5}'`;
- `isValidNick` — на тех же случаях, что в лабораторной 6;
- `validateText` пропускает 1000 эмодзи и отклоняет 1001.

### Упражнение 3. Асинхронные тесты

Протестируйте `delay` и `withTimeout` из лабораторной 4:

- быстрый промис проходит сквозь `withTimeout` со своим значением;
- медленный отклоняется с `{ code: 'ETIMEDOUT' }`;
- ошибка исходного промиса проходит как есть;
- `delay(60_000)` с фиктивными таймерами выполняется мгновенно.

### Упражнение 4. События и хуки

Протестируйте `Ticker` из лабораторной 5. Создавайте его в `beforeEach`,
а в `afterEach` останавливайте: даже упавший тест не должен оставлять
работающий таймер. Проверьте последовательность тиков и ошибку при `failAt`.

### Упражнение 5. Сломайте код

Внесите в `parsePort` ошибку (например, уберите проверку `/^\d+$/`)
и запустите тесты. Какие упали? Прочитайте, как `node:test` показывает
разницу между ожидаемым и полученным. Верните код обратно.

## Шаг проекта

1. Перенесите тесты из упражнений 1 и 2 в свой проект: `test/cli.test.js`
   и `test/protocol.test.js`.
2. Добавьте в `package.json` скрипт
   `"test": "node --test --test-timeout=10000 \"test/**/*.test.js\""`.
   Шаблон `*.test.js` нужен, чтобы вспомогательные файлы в `test/`
   (как `fake-connection.js`) не запускались как тесты.
3. Убедитесь, что `npm test` проходит.

## Контрольные вопросы

1. Как `node:test` понимает, что тест упал?
2. Чем `assert.equal` отличается от `assert.deepEqual`? Почему лучше `node:assert/strict`?
3. Что будет, если забыть `await` перед `assert.rejects`?
4. Зачем `afterEach`, если можно убрать за собой в конце теста?
5. Почему тесты проверяют поведение, а не внутреннее устройство?
6. Почему в `package.json` указан шаблон `test/**/*.test.js`, а не просто папка `test`?
