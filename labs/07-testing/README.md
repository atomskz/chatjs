# Лабораторная 7. Автотесты: `node:test`

**Цель:** научиться писать автотесты встроенными средствами Node.js:
проверять обычные и асинхронные функции, ожидаемые исключения и события;
готовить и убирать окружение теста; запускать тесты одной командой.

**Понадобится:** лабораторные 2, 4, 5 и 6. Упражнения 1 и 2 пишите сразу
в проекте `chat/`, в папке `test/`: они проверяют ваши `lib/cli.js`
и `protocol.js`. Упражнения 3 и 4 — в песочницах `sandbox-04` и `sandbox-05`,
рядом с тем кодом, который проверяют.

**Примерное время:** 2 часа.

## Теория

### Зачем тесты

Тест — это программа, которая проверяет другую программу. Он запускается
за секунды и проверяет то, что руками пришлось бы перепроверять после
каждой правки. Главная польза тестов — смелость: можно переписать
модуль и через секунду узнать, что ничего не сломалось.

### `node:test` и `node:assert`

В Node.js всё для тестов уже есть, ставить ничего не нужно:

```js
import assert from 'node:assert/strict';
import { describe, test } from 'node:test'; // it — то же самое, что test
import { parsePort } from '../lib/cli.js';

describe('parsePort', () => {
  test('accepts 5000', () => {
    assert.equal(parsePort('5000'), 5000);
  });
});
```

Тест считается упавшим, если внутри него выброшено исключение.
Проверки `assert` как раз выбрасывают исключение, когда условие не выполнено.

| проверка                            | что проверяет                                |
| ----------------------------------- | -------------------------------------------- |
| `assert.equal(a, b)`                | `a === b`                                    |
| `assert.deepEqual(a, b)`            | объекты или массивы совпадают по содержимому |
| `assert.ok(value)`                  | значение истинно                             |
| `assert.match(text, /re/)`          | строка подходит под регулярное выражение     |
| `assert.throws(fn, expected)`       | `fn()` выбрасывает подходящую ошибку         |
| `await assert.rejects(p, expected)` | промис отклоняется подходящей ошибкой        |

`expected` у `throws` и `rejects` бывает разным:

- класс — `assert.throws(fn, UsageError)`;
- объект с ожидаемыми полями — `{ code: 'ETIMEDOUT' }`;
- регулярное выражение для `message` — `/longer/`;
- функция-проверка: получает ошибку и возвращает `true`, если она подходит
  (или сама падает на `assert` внутри).

Если нужно проверить **и класс, и текст**, нужна функция:

```js
assert.throws(
  () => requireOption({}, 'port'),
  (error) => error instanceof UsageError && error.message === 'Option --port is required',
);
```

Объект `{ name: 'UsageError', message: '...' }` здесь не сработает: класс
`class UsageError extends Error {}` из лабораторной 2 не задаёт `name`,
и у его ошибок `name` равно `'Error'`. К тому же объект не проверяет класс.

Последним аргументом любой проверки можно передать текст. Он напечатается,
если проверка не прошла, — удобно в цикле, чтобы видеть, на каком значении
упало: `assert.equal(isValidNick(nick), false, nick)`.

Модуль `node:assert/strict` важнее, чем кажется: в нём `equal` сравнивает
через `===`. В нестрогом `node:assert` проверка `assert.equal(1, '1')` проходит.

### Асинхронные тесты

Если функция теста `async`, `node:test` дождётся её промиса:

```js
test('connects', async () => {
  const connection = await connect({ host: '127.0.0.1', port });
  assert.equal(await nextMessage(connection), 'hello');
});
```

Забытый `await` перед `assert.rejects` — частая ошибка: тест закончится
раньше, чем проверка выполнится, и сам тест покажет ✔. Дальше два варианта:

- если проверка не прошла бы, `node:test` позже напишет «generated
  asynchronous activity after the test ended...» с текстом ошибки и отметит
  весь файл как упавший;
- если прошла бы — никакого сообщения не будет. Тест «зелёный», но на самом
  деле ничего не проверял, и сломанный код он тоже пропустил бы.

Увидели «asynchronous activity after the test ended» — ищите пропущенный `await`.

### Табличные тесты

Однотипные случаи удобно описать массивом и создать тесты в цикле:

```js
for (const input of ['0', '65536', 'abc', '']) {
  test(`rejects "${input}"`, () => {
    assert.throws(() => parsePort(input), UsageError);
  });
}
```

### Подготовка и уборка: хуки

```js
import { afterEach, beforeEach, describe, test } from 'node:test';

describe('server', () => {
  let server;
  beforeEach(async () => {
    server = await startServer(); // перед каждым тестом в этом describe
  });
  afterEach(async () => {
    await server.stop(); // после каждого теста, даже если тест упал
  });
  test('...', async () => {
    /* server уже запущен */
  });
});
```

`before` и `after` работают так же, но один раз на весь `describe`.
Уборку для одного конкретного теста регистрируют через `t.after`:

````js
test('uses a temporary server', async (t) => {
  const server = await startServer();
  t.after(() => server.stop()); // выполнится после этого теста при любом исходе
  // ...
});
``` Неубранный сервер или таймер — частая причина
того, что тесты «зависают» после последнего теста.

### Фиктивное время

Тест `delay(60_000)` не должен ждать минуту. Для этого таймеры подменяют:

```js
test('waits a minute', async (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] }); // с этого места setTimeout — поддельный
  const promise = delay(60_000, 'done');
  t.mock.timers.tick(60_000); // «перемотать» время: таймер срабатывает сразу
  assert.equal(await promise, 'done'); // промис всё равно нужно дождаться
});
````

`t` — объект текущего теста, его передают первым аргументом. `tick()`
синхронный: он вызывает сработавшие таймеры, но промисы выполняются
чуть позже, поэтому `await` остаётся. После теста подмена снимается сама.

### Запуск

```bash
node --test                          # найти и запустить *.test.js и тесты в папке test/
node --test "test/**/*.test.js"      # только файлы по шаблону
node --test --watch                  # перезапускать при изменении файлов
node --test --test-timeout=10000     # упавший по таймауту тест не повесит весь прогон
```

Шаблон в кавычках раскрывает сам Node.js, поэтому команда одинаково
работает в bash и в PowerShell. В `package.json` её кладут в скрипт `test`
и запускают через `npm test`.

### Что тестировать

Тестируйте **поведение через публичный интерфейс**: «на вход `'abc'` —
ошибка `UsageError`», а не «внутри вызывается регулярное выражение».
Тогда тест не придётся переписывать при каждом рефакторинге.
