# Лабораторная 14. Корректное завершение: сигналы, таймеры, ресурсы

**Цель:** понять, когда процесс Node.js завершается сам и что его держит;
научиться обрабатывать Ctrl+C и `SIGTERM`, аккуратно выключать сервер
и не зависать на собеседнике, который не отвечает.

**Понадобится:** лабораторные 4, 10 и 13.

**Примерное время:** 2 часа.

## Теория

### Когда процесс завершается сам

Node.js завершает процесс, когда в цикле событий не осталось ничего,
что может вызвать обработчик:

| держит процесс                | как отпустить                                  |
| ----------------------------- | ---------------------------------------------- |
| `setTimeout`, `setInterval`   | `clearTimeout` / `clearInterval` или `unref()` |
| сервер, слушающий порт        | `server.close()`                               |
| открытый сокет                | `socket.end()` / `socket.destroy()`            |
| `readline` на `process.stdin` | `rl.close()`                                   |

`process.getActiveResourcesInfo()` показывает, что держит процесс прямо сейчас.

Отсюда главное правило: **правильная программа завершается сама**,
когда закрыла всё, что открыла. `process.exit()` — аварийный выход:
он обрывает несделанную работу (лабораторная 2) и прячет утечки ресурсов.

### Сигналы

Сигнал — это способ, которым ОС или другая программа просит процесс
что-то сделать:

| сигнал    | откуда                                                    | по умолчанию              |
| --------- | --------------------------------------------------------- | ------------------------- |
| `SIGINT`  | Ctrl+C в терминале                                        | завершить процесс         |
| `SIGTERM` | `kill <pid>`, systemd, `docker stop`, менеджеры процессов | завершить процесс         |
| `SIGKILL` | `kill -9 <pid>`                                           | убить, перехватить нельзя |

```js
process.once('SIGINT', stop); // теперь Ctrl+C не убивает процесс, а вызывает stop
process.once('SIGTERM', stop);
```

Как только на сигнал подписан обработчик, поведение по умолчанию
отключается: процесс **не** завершится, пока вы сами не закроете ресурсы.
`once` вместо `on` оставляет запасной выход: после первого сигнала
обработчик снимается, и второй Ctrl+C снова завершит процесс
по умолчанию.

**Особенности Windows.** Ctrl+C в консоли работает как `SIGINT`.
Сигнал `SIGTERM` Windows не отправляет: `process.kill(pid, 'SIGTERM')`
и Диспетчер задач завершают процесс без всяких обработчиков.

**Ctrl+C и `readline`.** В интерактивном терминале Ctrl+C перехватывает
`readline` и испускает событие `SIGINT` на самом `rl` (лабораторная 9).
До `process` сигнал доходит, только если ввод не из терминала, например
из файла. Клиенту нужны оба обработчика.

### Аккуратное выключение сервера

Порядок действий:

1. `server.close()` — перестать принимать новые подключения. Его колбэк
   сработает, когда закроется **последнее** открытое соединение;
2. предупредить клиентов («Server is shutting down»);
3. штатно закрыть соединения (`end()`, WebSocket `close(1000)`);
4. **страховка**: таймер на 2 секунды, который принудительно рвёт
   соединения, оставшиеся открытыми. Собеседник может зависнуть или
   не закрыть свою сторону, и без страховки сервер ждал бы его вечно.
   Таймеру нужен `unref()`, чтобы он сам по себе не держал процесс;
5. дождаться колбэка `server.close` — и всё. Процесс завершится сам.

### Коды выхода клиента

Клиент тоже сообщает, как всё закончилось: `0` — пользователь вышел сам
(`/quit`, Ctrl+C), `1` — не удалось подключиться, отказ во входе или
«Connection to server lost». Удобно, если главный метод клиента возвращает
промис с кодом выхода:

```js
process.exitCode = await client.run();
```

## Упражнения

Решения лежат в [solution/](solution/).

### Упражнение 1. Что держит процесс

Напишите `alive.js` с режимами `interval`, `unref`, `server` и `server-close`.
Каждый режим выводит `process.getActiveResourcesInfo()`, а при завершении
сообщает, сколько миллисекунд жил процесс. Объясните, почему каждый
режим завершается или не завершается.

### Упражнение 2. Двойной Ctrl+C

Программа что-то делает (печатает раз в полсекунды). Первый Ctrl+C
запускает «очистку» на 3 секунды и печатает `press Ctrl+C again to force`.
Второй Ctrl+C во время очистки завершает процесс сразу с кодом 130.
Если второго нажатия не было, процесс завершается сам с кодом 0.

### Упражнение 3. Аккуратный TCP-сервер

Возьмите эхо-сервер из лабораторной 10 и добавьте выключение по `SIGINT`
и `SIGTERM` по порядку из теории. Проверьте три случая:

- без клиентов: Ctrl+C — `Server stopped` сразу;
- с клиентом `nc`: он получает `Server is shutting down`, соединение закрывается;
- с клиентом, который не закрывает свою сторону (в Node.js —
  `net.connect({ ..., allowHalfOpen: true })`): `Server stopped` приходит
  через 2 секунды, по страховочному таймеру.

Уберите `unref()` у страховочного таймера. Что изменилось в первом случае?
А если убрать сам таймер, что будет в третьем?

### Упражнение 4. Коды выхода

Проверьте коды выхода своих программ из прошлых лабораторных
(`echo $?` или `$LASTEXITCODE`). Везде ли ошибка даёт ненулевой код?
Есть ли в коде `process.exit()`, без которого можно обойтись?

## Шаг проекта

1. В `ChatServer` добавьте метод `shutdown()`: разослать `system`
   «Server is shutting down» и закрыть все соединения. Пока сервер
   выключается, «left the chat» не рассылать.
2. В транспорте `close()` соединения уже страхуется таймером
   (лабораторная 13). Проверьте, что у таймера есть `unref()`.
3. В `server.js` по `SIGINT` и `SIGTERM` вызовите `chat.shutdown()`,
   затем `await server.close()` и залогируйте `Server stopped`.
   Без `process.exit()`.
4. Проверьте: запустите сервер и два клиента (`wscat` или свой), нажмите
   Ctrl+C на сервере. Клиенты получили предупреждение и отключились,
   а сервер завершился сам с кодом 0.
