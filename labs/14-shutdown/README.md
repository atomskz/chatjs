**Цель:** понять, когда процесс Node.js завершается сам и что его держит;
научиться обрабатывать Ctrl+C и `SIGTERM`, аккуратно выключать сервер

## Занятие 1. Что держит процесс и как его остановить

### 1.1. Зачем

Сервер из лабораторной 13 работает, но остановить его можно только
Ctrl+C, и он просто исчезает: клиенты видят оборванное соединение
(код 1006), а не «сервер выключается». ТЗ требует большего: по Ctrl+C
или `SIGTERM` сервер предупреждает всех, закрывает соединения
и завершается **сам**, с кодом 0. А если какой-то клиент не отвечает,
сервер не должен ждать его вечно.

**Аналогия: магазин закрывается на ночь.**

- Сначала запирают вход: новых покупателей не пускают (`server.close()`).
- Тем, кто внутри, объявляют: «Магазин закрывается» (`system`-сообщение).
- Ждут, пока все выйдут (`end()`, `close(1000)`).
- Того, кто через пять минут всё ещё бродит между полками, выводит охрана
  (страховочный таймер, `destroy()`).
- Когда внутри никого нет, гасят свет и уходят. Ночевать в магазине
  при этом никто не обязан: всё закончилось само (процесс завершается сам).

Чтобы так сделать, надо понимать, почему процесс Node.js вообще живёт
и когда он заканчивается.

### 1.2. Когда процесс завершается сам

Вы уже видели это в лабораторной 4: скрипт из одной строки `console.log`
завершается сразу, а сервер работает, пока его не остановят. Node.js
завершает процесс, когда в цикле событий не осталось ничего, что может
когда-нибудь вызвать обработчик:

| держит процесс                | как отпустить                                  |
| ----------------------------- | ---------------------------------------------- |
| `setTimeout`, `setInterval`   | `clearTimeout` / `clearInterval` или `unref()` |
| сервер, слушающий порт        | `server.close()`                               |
| открытый сокет                | `socket.end()` / `socket.destroy()`            |
| `readline` на `process.stdin` | `rl.close()`                                   |

Что держит процесс прямо сейчас, показывает `process.getActiveResourcesInfo()`.
Она возвращает массив имён:

| имя             | что это                                     |
| --------------- | ------------------------------------------- |
| `Timeout`       | таймер `setTimeout` / `setInterval`         |
| `TCPServerWrap` | сервер, слушающий порт                      |
| `TCPSocketWrap` | открытое TCP-соединение                     |
| `TTYWrap`       | терминал (например, `stdin` под `readline`) |

**`unref()`** говорит таймеру (или серверу, или сокету): «работай, но процесс
ради тебя не держи». Если кроме таких объектов ничего не осталось, процесс
завершается, и таймер просто не сработает. Таймеры с `unref()` в списке
`getActiveResourcesInfo()` не показываются.

**Событие `exit`.** Перед самым завершением процесс испускает событие `exit`
с кодом выхода:

```js
process.on('exit', (code) => console.log(`exit with ${code}`));
```

В его обработчике можно только что-то быстро сделать **синхронно**.
Асинхронная работа там уже не выполнится:

```js
process.on('exit', () => {
  setTimeout(() => console.log('never'), 0);
  console.log('exit handler ran');
});
```

```
exit handler ran
```

`never` не напечатано: цикл событий уже остановлен, таймеры не сработают.

### 1.3. Разобранный пример: что держит процесс

`alive.js` запускает в разных режимах разные ресурсы, печатает
`getActiveResourcesInfo()`, а в `exit` — сколько прожил процесс:

```js
import net from 'node:net';

const mode = process.argv[2] ?? 'unref';
const start = Date.now();
process.on('exit', (code) => console.log(`exit after ${Date.now() - start} ms, code ${code}`));

switch (mode) {
  case 'interval':
    setInterval(() => console.log('still here'), 1000);
    break;
  case 'unref':
    setInterval(() => console.log('never printed'), 1000).unref();
    break;
  case 'server':
  case 'server-close': {
    const server = net.createServer().listen(0);
    if (mode === 'server-close') {
      setTimeout(() => server.close(() => console.log('server closed')), 1000);
    }
    break;
  }
}

console.log('active resources:', process.getActiveResourcesInfo());
```

Запуски по очереди:

```
$ node alive.js interval
active resources: [ 'Timeout' ]
still here
still here
...                              (пока не нажмёте Ctrl+C)

$ node alive.js unref
active resources: []
exit after 1 ms, code 0

$ node alive.js server
active resources: [ 'TCPServerWrap' ]
                                 (молчит, пока не нажмёте Ctrl+C)

$ node alive.js server-close
active resources: [ 'TCPServerWrap', 'Timeout' ]
server closed
exit after 1012 ms, code 0
```

Разбор:

- **`interval`** — таймер срабатывает вечно, процессу всегда есть что ждать.
- **`unref`** — тот же таймер, но с `unref()`. Список пуст, процесс
  завершился через 1 мс, и `never printed` не напечатано ни разу.
- **`server`** — сервер слушает порт: в любой момент может подключиться
  клиент, и нужно будет вызвать обработчик. Процесс ждёт.
- **`server-close`** — держат двое, сервер и таймер на 1 секунду. Таймер
  сработал и закрыл сервер, держать стало нечему, процесс завершился сам
  через ~1000 мс с кодом 0. Никакого `process.exit()`.

Отсюда главное правило: **правильная программа завершается сама**,
когда закрыла всё, что открыла. `process.exit()` — аварийный выход:
он обрывает несделанную работу (например, недописанный вывод,
лабораторная 2) и прячет утечки: если процесс без него не завершается,
значит, что-то осталось открытым, и это надо найти, а не замаскировать.

### 1.4. Сигналы

Сигнал — это способ, которым ОС или другая программа просит процесс
что-то сделать. Обычно — завершиться:

| сигнал    | откуда                                                    | по умолчанию              |
| --------- | --------------------------------------------------------- | ------------------------- |
| `SIGINT`  | Ctrl+C в терминале                                        | завершить процесс         |
| `SIGTERM` | `kill <pid>`, systemd, `docker stop`, менеджеры процессов | завершить процесс         |
| `SIGKILL` | `kill -9 <pid>`                                           | убить, перехватить нельзя |

В Node.js сигналы приходят как события объекта `process`:

```js
process.once('SIGINT', stop); // теперь Ctrl+C не убивает процесс, а вызывает stop
process.once('SIGTERM', stop);
```

Обработчик получает имя сигнала: `stop('SIGINT')`. Три правила:

1. **Подписались — значит, отменили поведение по умолчанию.** Сигнал больше
   не убивает процесс, а только вызывает ваш обработчик. Дальше процесс
   живёт, пока его держат ресурсы, и завершится сам, когда вы их закроете.
   Если обработчик ничего не закрывает, Ctrl+C просто перестаёт работать.
2. **Обработчик сигнала процесс не держит.** Программа с одним
   `process.on('SIGINT', ...)` и без таймеров и сокетов сразу завершится
   с кодом 0, не дожидаясь никакого Ctrl+C.
3. **`once` вместо `on` оставляет запасной выход.** После первого сигнала
   обработчик снимается, и второй Ctrl+C снова завершит процесс по умолчанию.
   Если ваше выключение зависло, пользователь не останется с процессом,
   который не убить.

**Код 130.** Если процесс убит сигналом, оболочка показывает код выхода
`128 + номер сигнала`: для `SIGINT` (номер 2) — 130, для `SIGTERM` (15) — 143.
Программу, которая сама выходит «по Ctrl+C» принудительно, принято
завершать с тем же кодом: `process.exit(130)`. Так скрипты, которые её
запускают, понимают, что её прервал пользователь.

**Особенности Windows.** Обработчики получают только настоящий Ctrl+C
в окне консоли. `process.kill(pid, 'SIGTERM')`, `process.kill(pid, 'SIGINT')`,
`kill` из Git Bash и Диспетчер задач завершают процесс `node.exe` сразу,
без всяких обработчиков. Поэтому `SIGTERM` проверяйте в Linux или macOS,
а в Windows — только Ctrl+C.

**Ctrl+C и `readline`.** В интерактивном терминале Ctrl+C перехватывает
`readline` и испускает событие `SIGINT` на самом `rl` (лабораторная 9),
а до `process` сигнал не доходит. До `process` он доходит, только если ввод
не из терминала, например из файла или через `|`. Клиенту чата нужны
оба обработчика.

### 1.5. Разобранный пример: двойной Ctrl+C

Программа работает (печатает раз в полсекунды). Первый Ctrl+C запускает
«очистку» на 3 секунды. Если пользователь не хочет ждать, второй Ctrl+C
завершает процесс сразу:

```js
const work = setInterval(() => console.log('working...'), 500);

async function cleanup() {
  console.log('Shutting down, press Ctrl+C again to force');
  clearInterval(work);
  await new Promise((resolve) => setTimeout(resolve, 3000)); // «сохраняем данные»
  console.log('Cleanup finished');
}

process.once('SIGINT', () => {
  process.once('SIGINT', () => {
    console.log('Forced exit');
    process.exit(130);
  });
  cleanup();
});
```

Одно нажатие:

```
$ node double-ctrl-c.js
working...
^CShutting down, press Ctrl+C again to force
Cleanup finished                 (через 3 секунды)
$ echo $?
0
```

Два нажатия:

```
$ node double-ctrl-c.js
working...
^CShutting down, press Ctrl+C again to force
^CForced exit
$ echo $?
130
```

Разбор:

- После первого Ctrl+C работает внешний обработчик. Он снимается
  (`once`) и тут же подписывает внутренний — на следующий сигнал.
- `cleanup` останавливает `setInterval`. Теперь процесс держит только
  таймер на 3 секунды. Когда он сработает, держать нечего: процесс
  завершится сам с кодом 0. `process.exit` для этого не нужен.
- Второй Ctrl+C попадает во внутренний обработчик. Здесь `process.exit(130)`
  уместен: пользователь **сам** попросил бросить незаконченную работу.

В PowerShell код выхода смотрят через `$LASTEXITCODE` вместо `$?`.

## Занятие 2. Аккуратное выключение сервера

### 2.1. Порядок действий

1. `server.close()` — перестать принимать новые подключения. Его колбэк
   (или промис) сработает, когда закроется **последнее** уже открытое
   соединение;
2. предупредить клиентов («Server is shutting down»);
3. штатно закрыть соединения (`end()`, WebSocket `close(1000)`);
4. **страховка**: таймер на 2 секунды, который принудительно рвёт
   соединения, оставшиеся открытыми. Собеседник может зависнуть или
   не закрыть свою сторону, и без страховки сервер ждал бы его вечно.
   Таймеру нужен `unref()`, чтобы он сам по себе не держал процесс;
5. дождаться колбэка `server.close` — и всё. Процесс завершится сам.

```
время ──────────────────────────────────────────────────────────►
SIGINT
  │ 1. server.close()        новых не пускаем
  │ 2. «Server is shutting down» всем
  │ 3. end() / close(1000) каждому
  │ 4. таймеры 2 с (unref)
  │
  ├── вежливые клиенты закрылись ──► колбэк server.close ──► «Server stopped»
  │                                                           процесс завершился сам
  └── «зависший» клиент ─── 2 с ───► destroy() ──► колбэк server.close ──► ...
```

Шаги 1–3 можно делать в любом порядке: они выполняются синхронно, одним
куском кода, и новый клиент не успеет подключиться между ними. В эталонном
`server.js` сначала вызывается `chat.shutdown()` (шаги 2–3), а потом
`server.close()` (шаг 1). Важно другое: **ждать** (шаг 5) нужно после того,
как все соединения получили команду закрыться, иначе ожидание не закончится.

### 2.2. Разобранный пример: аккуратный TCP-сервер

Эхо-сервер из лабораторной 10 с выключением. Сокеты храним в `Set`,
чтобы при выключении пройти по всем:

```js
import { once } from 'node:events';
import net from 'node:net';

const port = Number(process.argv[2] ?? 5000);
const CLOSE_TIMEOUT_MS = 2000;
const sockets = new Set();

const server = net.createServer((socket) => {
  sockets.add(socket);
  socket.write('Welcome! Type something.\n');
  socket.on('data', (chunk) => socket.write(`echo: ${chunk}`));
  socket.on('error', () => {});
  socket.on('close', () => sockets.delete(socket));
});

server.listen(port);
await once(server, 'listening');
console.log(`listening on port ${port}, press Ctrl+C to stop`);

async function stop(signal) {
  console.log(`${signal} received, shutting down...`);

  const closed = new Promise((resolve) => server.close(resolve)); // 1
  for (const socket of sockets) {
    socket.end('Server is shutting down\n'); // 2 и 3: end может отправить последние данные
    setTimeout(() => socket.destroy(), CLOSE_TIMEOUT_MS).unref(); // 4
  }

  await closed; // 5
  console.log('Server stopped');
}

process.once('SIGINT', stop); // Ctrl+C
process.once('SIGTERM', stop); // kill, systemd, docker stop
```

**Случай 1. Вежливый клиент.** Подключитесь `nc.js` из лабораторной 10
и нажмите Ctrl+C на сервере (в примере Ctrl+C нажат через секунду после
запуска сервера, время клиента — от его подключения):

```
сервер:
listening on port 5000, press Ctrl+C to stop
SIGINT received, shutting down...
Server stopped
                                 процесс завершился через 1.0 с после запуска

клиент:
0.0s got: Welcome! Type something.
0.7s got: Server is shutting down
0.7s closed
```

Клиент получил FIN и закрыл свою сторону (так `net` делает по умолчанию),
последнее соединение закрылось, колбэк `server.close` сработал. Страховочные
таймеры не понадобились, и благодаря `unref()` процесс их не ждал.

**Случай 2. Невежливый клиент.** [solution/half-open-client.js](solution/half-open-client.js)
подключается с `allowHalfOpen: true`: получив FIN, он **не** закрывает свою
сторону. Чтобы его процесс сам не завершился (тогда ОС закрыла бы сокет
за него), его держит пустой `setInterval`:

```
сервер:
listening on port 5000, press Ctrl+C to stop
SIGINT received, shutting down...
Server stopped                   через 2 с после SIGINT
                                 процесс завершился через 3.0 с после запуска

клиент:
0.0s got: Welcome! Type something.
0.7s got: Server is shutting down
0.7s server sent FIN, but I keep my side open
                                 (больше ничего, остановите Ctrl+C)
```

Соединение не закрылось, `server.close` ждал. Через 2 секунды сработал
страховочный таймер, `destroy()` закрыл сокет, и сервер завершился.

**Что будет без страховки или без `unref()`** (проверено теми же клиентами):

Сколько процесс сервера живёт после `SIGINT`:

| вариант              | вежливый клиент                                | невежливый клиент             |
| -------------------- | ---------------------------------------------- | ----------------------------- |
| как в примере        | сразу завершился                               | 2 с, до страховочного таймера |
| таймер без `unref()` | «Server stopped» сразу, но процесс жил ещё 2 с | 2 с                           |
| без таймера          | сразу завершился                               | **вечно**, пока жив клиент    |

Без `unref()` «Server stopped» печатается вовремя, но процесс ещё 2 секунды
ждёт таймеры, которым уже нечего делать. Без таймера сервер зависает
навсегда: в нашем опыте он завершился, только когда убили клиента.

### 2.3. Коды выхода клиента

Клиент тоже сообщает, как всё закончилось: `0` — пользователь вышел сам
(`/quit`, Ctrl+C), `1` — не удалось подключиться, отказ во входе или
«Connection to server lost». Удобно, если главный метод клиента возвращает
промис с кодом выхода:

```js
process.exitCode = await client.run();
```

`process.exitCode` — не `process.exit()`: он только запоминает код,
с которым процесс завершится, когда закроет всё сам.

## Типичные ошибки

| что видите                                          | почему                                                                   | что делать                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| после `Server stopped` процесс не завершается       | что-то осталось открытым: таймер, сокет, `readline`                      | вывести `getActiveResourcesInfo()` и закрыть найденное            |
| Ctrl+C больше ничего не делает                      | обработчик `SIGINT` подписан, но ничего не закрывает                     | закрыть ресурсы в обработчике; `once` вместо `on`                 |
| `Server stopped` не печатается никогда              | `await` колбэка `server.close` до закрытия соединений, или нет страховки | сначала закрыть все соединения, потом ждать; таймер с `destroy()` |
| после `Server stopped` ещё 2 секунды тишины         | у страховочного таймера нет `unref()`                                    | `setTimeout(...).unref()`                                         |
| клиенты не получили «Server is shutting down»       | соединения порваны `destroy()` или `process.exit()` сразу                | сначала `end()` / `close(1000)`, `destroy()` — только по таймеру  |
| при выключении все получили пачку «X left the chat» | `#handleDisconnect` не знает, что идёт выключение                        | флаг `#isShuttingDown`                                            |
| `SIGTERM` в Windows убивает сервер без обработчика  | так устроена Windows                                                     | `SIGTERM` проверять в Linux/macOS, в Windows — Ctrl+C             |
| в клиенте Ctrl+C не вызывает `process.on('SIGINT')` | в терминале сигнал перехватывает `readline`                              | подписаться и на `rl.on('SIGINT')`                                |
| после выхода пропал конец вывода                    | `process.exit()` обрывает несделанную запись                             | `process.exitCode = ...` и дать процессу завершиться самому       |

## Шаг проекта

1. Замените временный `shutdown()` из лабораторной 13 настоящим:

   ```js
   // поля и методы класса ChatServer
   #isShuttingDown = false;

   shutdown() {
     this.#isShuttingDown = true;
     this.#broadcast(ServerMessage.system('Server is shutting down'));
     for (const connection of this.#clients.keys()) {
       connection.close();
     }
   }
   ```

   В `#handleDisconnect` при поднятом флаге «left the chat» не рассылайте:
   все и так уходят. Теперь в `npm test` проходят все тесты, включая тесты
   выключения `warns everyone and closes connections on shutdown`.

2. В транспорте `close()` соединения уже страхуется таймером
   (лабораторная 13). Проверьте, что у таймера есть `unref()`.

3. В `server.js` в конце `main()` добавьте выключение:

   ```js
   const stop = async () => {
     logger.info('Shutting down...');
     chat.shutdown();
     await server.close(); // транспорт сам рвёт соединения, не закрывшиеся за 2 с
     logger.info('Server stopped');
   };
   process.once('SIGINT', stop); // Ctrl+C
   process.once('SIGTERM', stop); // kill, остановка из менеджера процессов
   ```

   Без `process.exit()`.

4. **Проверка вручную.** Запустите сервер и два клиента (`wscat` или свой),
   войдите как `alice` и `bob` и нажмите Ctrl+C на сервере. Эталон выводит:

   ```
   2026-10-29T00:21:36.836Z INFO  Server listening on port 5300 (transport: ws)
   2026-10-29T00:21:37.367Z INFO  Joined: alice (::1:61654)
   2026-10-29T00:21:37.616Z INFO  Joined: bob (::1:61655)
   2026-10-29T00:21:38.316Z INFO  Shutting down...
   2026-10-29T00:21:38.318Z INFO  Server stopped
   2026-10-29T00:21:38.318Z INFO  Disconnected: bob (::1:61655)
   2026-10-29T00:21:38.318Z INFO  Disconnected: alice (::1:61654)
   ```

   (строки `Connected:` пропущены.) Каждый клиент получил
   `{"type":"system","text":"Server is shutting down",...}` и закрытие
   с кодом 1000, а не 1006. Сообщений «left the chat» нет. Сервер
   завершился сам, `echo $?` показывает 0. Повторите на `--transport tcp`.

5. Сделайте коммит.

## Контрольные вопросы

1. Почему процесс с работающим сервером не завершается, а скрипт без таймеров — завершается?
2. Что делает `unref()` и почему страховочному таймеру он нужен?
3. Что изменится, если подписаться на `SIGINT`, но ничего не закрыть?
4. Почему `process.once('SIGINT')` безопаснее, чем `process.on('SIGINT')`?
5. Зачем нужен страховочный таймер при закрытии соединений?
6. Почему в сервере нет `process.exit()`?
7. Когда Ctrl+C приходит в `rl.on('SIGINT')`, а когда — в `process.on('SIGINT')`?
8. Чем `process.exitCode = 1` отличается от `process.exit(1)`?
