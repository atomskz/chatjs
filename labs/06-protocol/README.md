# Лабораторная 6. JSON и протокол сообщений

**Цель:** научиться описывать прикладной протокол — договорённость о том,
какими сообщениями обмениваются сервер и клиент. Разобраться, как
передавать объекты строкой через JSON и чего JSON не умеет, почему данным
из сети нельзя доверять, как проверять строки регулярными выражениями
и что на самом деле значит «длина строки».

**Понадобится:** лабораторная 3 (классы ошибок). Упражнения делайте в папке
`sandbox-06` с `"type": "module"`, шаг проекта — в `chat/`.

**Примерное время:** 3–4 часа, два занятия.

**Как работать:** каждый пример запускайте у себя и сверяйте вывод.
В разминках сначала запишите **свой** ответ, потом проверьте и только
потом смотрите [answers.md](answers.md).

## Занятие 1. JSON и недоверенные данные

### 1.1. Зачем: общий язык

Сервер и клиент чата — разные программы, часто на разных компьютерах.
По сети между ними ходят только байты и строки. Чтобы они понимали друг
друга, нужна договорённость: какие бывают сообщения, какие в них поля
и что делать с неправильными. Эта договорённость называется
**прикладным протоколом**.

**Аналогия: бланки в учреждении.** Заявление на отпуск, справка, жалоба —
у каждого вида бланка свои поля, а в углу написано, что это за бланк.
Сотрудник смотрит на вид бланка и понимает, какие поля читать и что
с ним делать. В чате «вид бланка» — поле `type`, а поля бланка —
остальные поля сообщения:

```json
{ "type": "msg", "text": "Привет всем!" }
{ "type": "join", "nick": "alice" }
```

Протокол удобно держать в одном модуле, общем для сервера и клиента.
Тогда стороны не разойдутся в формате. И протокол ничего не знает о сети:
он превращает объект в строку и обратно, а как строка доедет до
собеседника — забота транспорта (лабораторные 10–13).

### 1.2. JSON: объект ↔ строка

Объект JavaScript нельзя «просто отправить»: по сети идут только строки
и байты. JSON — общепринятый способ записать данные строкой.

```
отправитель                                       получатель
{ type: 'msg', text: 'hi' }                       { type: 'msg', text: 'hi' }
        │ JSON.stringify                                   ▲ JSON.parse
        ▼                                                  │
'{"type":"msg","text":"hi"}'  ──── по сети строкой ────►  '{"type":"msg","text":"hi"}'
```

```js
JSON.stringify({ type: 'msg', text: 'hi' }); // '{"type":"msg","text":"hi"}'
JSON.parse('{"type":"msg","text":"hi"}'); // { type: 'msg', text: 'hi' }
```

Если отправить объект без `JSON.stringify`, получится не то: `String(obj)`
и шаблонная строка `` `${obj}` `` дают `'[object Object]'`, а `socket.write(obj)`
вообще выбросит `TypeError: The "chunk" argument must be of type string or an instance of Buffer, ...`.

**JSON — это не JavaScript.** Чего в нём нет:

| значение              | после `JSON.stringify`                      |
| --------------------- | ------------------------------------------- |
| `undefined` в объекте | поле пропадает                              |
| `undefined` в массиве | `null`                                      |
| функция               | поле пропадает                              |
| `NaN`, `Infinity`     | `null`                                      |
| `Date`                | строка ISO; после `parse` это уже не `Date` |
| `BigInt`              | `TypeError`                                 |

`JSON.parse` выбрасывает `SyntaxError` на любой ошибке: одинарные кавычки,
висячая запятая, пустая строка, просто текст. И он прекрасно разбирает
не только объекты: `'null'`, `'42'`, `'"hi"'` и `'[1,2]'` — тоже правильный JSON.

Перевод строки внутри значения `JSON.stringify` записывает как `\n`
(два символа). Поэтому в закодированном JSON настоящего перевода строки
не бывает. Это пригодится в лабораторной 11.

### 1.3. Данным из сети доверять нельзя

**Зачем.** Подключиться к серверу может кто угодно и прислать что угодно:
опечатку, мусор, специально испорченные данные. Сервер, который падает
от одного кривого сообщения, отключит всех.

**Разобранный пример.** Наивный разбор:

```js
function getType(text) {
  return JSON.parse(text).type;
}
```

| вход               | результат                                                      |
| ------------------ | -------------------------------------------------------------- |
| `'{"type":"msg"}'` | `'msg'` — всё хорошо                                           |
| `'hello'`          | `SyntaxError: Unexpected token 'h', "hello" is not valid JSON` |
| `'null'`           | `TypeError: Cannot read properties of null (reading 'type')`   |
| `'[1]'`            | `undefined` — у массива нет поля `type`                        |
| `'{"type":5}'`     | `5` — тип есть, но это не строка                               |

Каждое входящее сообщение нужно проверить по шагам:

1. это правильный JSON?
2. это объект? Не `null`, не массив, не число (`typeof null === 'object'`!)
3. есть ли строковое поле `type`?
4. знаем ли мы такой `type`?
5. правильные ли поля у этого типа?

```js
function safeParseMessage(text) {
  let data;
  try {
    data = JSON.parse(text);
  } catch {
    return { ok: false, error: 'not valid JSON' }; // шаг 1
  }
  const isObject = typeof data === 'object' && data !== null && !Array.isArray(data);
  if (!isObject) {
    return { ok: false, error: 'not a JSON object' }; // шаг 2
  }
  if (typeof data.type !== 'string') {
    return { ok: false, error: 'field "type" must be a string' }; // шаг 3
  }
  return { ok: true, value: data };
}
```

Шаги 1–3 — общая форма, их делает функция разбора (в проекте — `decode`).
Шаги 4–5 зависят от сообщения, их делает тот, кто его обрабатывает.
Почему не всё сразу: модуль протокола общий, а сервер и клиент принимают
**разные** наборы типов (сервер — `join`, `msg`..., клиент — `welcome`,
`users`...). К тому же часть проверок зависит от состояния: `msg` до `join` —
ошибка, а после — нет. Это уже логика чата, и протоколу о ней знать не нужно.

## Занятие 2. Формат сообщений, регулярные выражения, длина строк

### 2.1. Сообщения чата

Формат сообщений задан в разделе 5 [ТЗ](../15-chat/chat-tz.md#5-протокол-обмена).
Одно сообщение — один JSON-объект с обязательным полем `type`:

| клиент → сервер | поля   | назначение                               |
| --------------- | ------ | ---------------------------------------- |
| `join`          | `nick` | первое сообщение после подключения, вход |
| `msg`           | `text` | сообщение в общий чат                    |
| `list`          | —      | запрос списка участников                 |
| `leave`         | —      | корректный выход                         |

| сервер → клиент | поля                 | назначение                                      |
| --------------- | -------------------- | ----------------------------------------------- |
| `welcome`       | `users: string[]`    | успешный вход, список участников                |
| `error`         | `code`, `message`    | ошибка: машиночитаемый код и текст для человека |
| `msg`           | `from`, `text`, `ts` | сообщение чата; `ts` — время сервера в мс       |
| `system`        | `text`, `ts`         | системное событие: вход или выход участника     |
| `users`         | `users: string[]`    | ответ на `list`                                 |

Пример обмена из ТЗ:

```
C→S {"type":"join","nick":"alice"}
S→C {"type":"welcome","users":["bob","alice"]}
S→* {"type":"system","text":"alice joined the chat","ts":1729425600000}
C→S {"type":"msg","text":"Привет всем!"}
S→* {"type":"msg","from":"alice","text":"Привет всем!","ts":1729425605000}
```

`S→*` значит «сервер — всем участникам».

### 2.2. Разобранный пример: конструкторы сообщений

**Было** — сообщения собираются руками в разных местах кода:

```js
send({ type: 'welcome', users: nicks });
// ...в другом файле, через неделю:
send({ type: 'welcom', user: nicks }); // две опечатки — и клиент молча ничего не покажет
```

**Стало** — формат каждого сообщения записан ровно в одном месте:

```js
export const ServerMessage = {
  welcome: (users) => ({ type: 'welcome', users }),
  msg: (from, text, ts = Date.now()) => ({ type: 'msg', from, text, ts }),
};

send(ServerMessage.welcome(['ann', 'bob'])); // опечатка в имени функции сразу даст ошибку
```

`(users) => ({ type: 'welcome', users })` — стрелочная функция, которая
возвращает объект: круглые скобки вокруг `{}` обязательны. `{ users }` —
краткая запись `{ users: users }`. `ts = Date.now()` — значение по умолчанию:
время ставится само, но тест может передать своё.

Получатель различает сообщения по `type` через `switch`:

```js
switch (message.type) {
  case 'welcome':
    showUsers(message.users);
    break;
  case 'msg':
    showMessage(message.from, message.text);
    break;
}
```

**Коды ошибок** — тоже константы, а не строки, разбросанные по коду.
Значение каждой константы — **та же строка**, что и её имя: код уходит
клиенту внутри JSON, и там должен быть понятный текст, а не число.

```js
export const ErrorCode = {
  BAD_MESSAGE: 'BAD_MESSAGE', // не JSON или нет строкового поля type
  UNKNOWN_TYPE: 'UNKNOWN_TYPE', // такого type нет
  NOT_JOINED: 'NOT_JOINED', // сообщение до join
  ALREADY_JOINED: 'ALREADY_JOINED', // повторный join
  INVALID_NICK: 'INVALID_NICK',
  NICK_TAKEN: 'NICK_TAKEN',
  INVALID_TEXT: 'INVALID_TEXT', // пустой или слишком длинный текст
  INTERNAL_ERROR: 'INTERNAL_ERROR', // баг на сервере
};

export const NICK_RULES = '1-20 characters: latin letters, digits, "_" or "-"';
```

Константа защищает от опечаток. Но коварно: опечатка в имени константы
(`ErrorCode.NIKC_TAKEN`) даёт `undefined`, а `JSON.stringify` такое поле
молча **пропускает**. Клиент получит `{"type":"error","message":"..."}` вообще
без кода. Поэтому коды проверяют тестами (лабораторная 7).

### 2.3. Регулярные выражения

**Зачем.** Ник должен состоять из 1–20 латинских букв, цифр, `_` или `-`.
Проверять это циклом по символам долго и легко ошибиться. Регулярное
выражение — короткий шаблон, которому строка либо соответствует, либо нет.

**Разобранный пример: строим шаблон ника по шагам.** `.test(строка)`
возвращает `true` или `false`:

| шаблон                    | `'alice'` | `'!!! a !!!'` | `'Bob_2'` | `''`    | 21 буква `a` |
| ------------------------- | --------- | ------------- | --------- | ------- | ------------ |
| `/[a-z]/`                 | `true`    | `true`        | `true`    | `false` | `true`       |
| `/^[a-z]+$/`              | `true`    | `false`       | `false`   | `false` | `true`       |
| `/^[A-Za-z0-9_-]+$/`      | `true`    | `false`       | `true`    | `false` | `true`       |
| `/^[A-Za-z0-9_-]{1,20}$/` | `true`    | `false`       | `true`    | `false` | `false`      |

1. `/[a-z]/` — «есть хотя бы одна маленькая латинская буква **где-нибудь**».
   Поэтому проходит даже `'!!! a !!!'`.
2. `^` и `$` — начало и конец строки, `+` — «один или больше раз». Теперь
   вся строка от начала до конца должна состоять из букв. Но `'Bob_2'`
   не проходит: заглавная буква, `_` и цифра не входят в набор.
3. Расширили набор в квадратных скобках: `A-Z`, `0-9`, `_`, `-`.
4. `{1,20}` вместо `+` — от 1 до 20 раз. Теперь 21 символ не проходит.

```js
const NICK_PATTERN = /^[A-Za-z0-9_-]{1,20}$/;
NICK_PATTERN.test('alice'); // true
```

| часть           | значит                                                               |
| --------------- | -------------------------------------------------------------------- |
| `^` и `$`       | начало и конец строки                                                |
| `[A-Za-z0-9_-]` | один символ из набора: латиница, цифры, `_`, `-`                     |
| `{1,20}`        | от 1 до 20 раз                                                       |
| `\d`, `\s`      | цифра, пробельный символ                                             |
| `.`             | любой символ, кроме перевода строки                                  |
| `*`, `+`, `?`   | 0 и больше раз, 1 и больше, 0 или 1                                  |
| `\.`, `\/`      | сам символ `.` или `/`: обратная косая отменяет особый смысл         |
| `/.../i`        | флаг `i`: без учёта регистра                                         |
| `/.../m`        | флаг `m`: `^` и `$` означают начало и конец каждой **строки** текста |

Без `^` и `$` выражение ищет совпадение где угодно — поэтому в тестах удобно
писать `assert.match(text, /longer/)`: «где-то в тексте есть `longer`».

В JavaScript `$` без флага `m` — это настоящий конец строки, поэтому
`'ann\n'` (с переводом строки в конце) шаблону ника не подходит. В некоторых
других языках `$` разрешает перевод строки перед концом. Именно поэтому
такой случай стоит проверять тестом.

Ещё два метода: `text.match(/\d+/)` находит совпадение, а
`text.split(/\s+/)` режет строку по шаблону (здесь — по пробелам любой длины).

### 2.4. Длина строки

**Зачем.** По ТЗ сообщение не длиннее 1000 символов. Но «символ» в JavaScript —
не то, что кажется: строки хранятся в UTF-16, и `.length` считает 16-битные
единицы, а не символы.

| текст        | `.length` | `[...text].length` | что видит человек | байт в UTF-8 |
| ------------ | --------- | ------------------ | ----------------- | ------------ |
| `hello`      | 5         | 5                  | 5                 | 5            |
| `привет`     | 6         | 6                  | 6                 | 12           |
| `😀`         | 2         | 1                  | 1                 | 4            |
| `👨‍👩‍👧` (семья) | 8         | 5                  | 1                 | 18           |

- `[...text]` разбивает строку на code points: так считать символы честнее.
- Символ, который видит человек (графема), может состоять из нескольких
  code points. Графемы считает `Intl.Segmenter`:
  `[...new Intl.Segmenter().segment(text)].length`.
- Одна и та же буква бывает записана по-разному: `é` — один code point
  (U+00E9) или два: `e` и знак ударения (U+0301). Выглядят одинаково,
  но `'\u00e9' === 'e\u0301'` — `false`. Привести строку к одной форме
  можно через `text.normalize('NFC')`.
- Байты в UTF-8 считает `Buffer.byteLength(text)`. Это важно для сети
  (лабораторная 11).

**Какой способ выбрать для ограничения «не длиннее 1000 символов».**
`.length` не подходит: эмодзи засчитывается за два. Графемы точнее всего
совпадают с тем, что видит человек, но считаются медленнее, а результат
может немного меняться между версиями Node.js (вместе с правилами Unicode).
Code points (`[...text].length`) — простой, быстрый и стабильный компромисс.
Его и использует проект. Байты считают, только когда ограничение
связано с сетью или хранилищем.

`[...text]` работает только для строк: для `undefined` будет
`TypeError: undefined is not iterable`. Поэтому сначала проверяют, что
пришла строка.

## Типичные ошибки

| что видите                                                                        | почему                                                      | что делать                                                 |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------- |
| `SyntaxError: Unexpected token 'h', "hello" is not valid JSON`                    | на вход пришёл не JSON                                      | `JSON.parse` в `try/catch`; ответить ошибкой `BAD_MESSAGE` |
| `SyntaxError: "[object Object]" is not valid JSON`                                | в `JSON.parse` передали объект, а не строку                 | разбирать только строку из сети; объект разбирать не нужно |
| `TypeError: Cannot read properties of null (reading 'type')`                      | пришло `'null'` — правильный JSON, но не объект             | проверять `data !== null` и `!Array.isArray(data)`         |
| получатель видит `[object Object]`                                                | объект отправлен без `JSON.stringify`                       | `encode(message)` перед отправкой                          |
| `TypeError: The "chunk" argument must be of type string or an instance of Buffer` | в `socket.write` передан объект                             | `socket.write(JSON.stringify(message))`                    |
| поле пропало после передачи                                                       | его значение было `undefined` (или функция)                 | задавать значения явно; проверять имена констант           |
| клиент получил `error` без `code`                                                 | опечатка в `ErrorCode.XXX` дала `undefined`, и поле пропало | тест на коды ошибок (лабораторная 7)                       |
| `ts.getHours is not a function`                                                   | дата пришла строкой или числом, а не `Date`                 | `new Date(ts)` на стороне получателя                       |
| ник `'ann!'` прошёл проверку                                                      | в шаблоне нет `^` и `$`                                     | `/^...$/`                                                  |
| `isValidNick(42)` вернул `true`                                                   | `test` превратил число в строку                             | сначала `typeof nick === 'string'`                         |
| 600 эмодзи «длиннее 1000 символов»                                                | `.length` считает эмодзи за два                             | `[...text].length`                                         |
| `TypeError: undefined is not iterable`                                            | `[...text]` для отсутствующего поля                         | проверить, что `text` — строка, до подсчёта                |

## Шаг проекта

Создайте в проекте `protocol.js` — общий модуль сервера и клиента:

- `MAX_TEXT_LENGTH = 1000`, `NICK_RULES` — правило для ника текстом
  (для сообщений об ошибках);
- `ErrorCode` — объект с кодами из 2.2, значение каждого — строка с тем же именем;
- `class ProtocolError extends Error` с конструктором `(code, message)`,
  полями `name = 'ProtocolError'` и `code`. Порядок аргументов важен:
  сервер будет пересылать клиенту `error.code` и `error.message`;
- `ClientMessage` и `ServerMessage` — конструкторы сообщений по таблицам
  из 2.1, ровно с такими аргументами:
  - `ClientMessage.join(nick)`, `msg(text)`, `list()`, `leave()`;
  - `ServerMessage.welcome(users)`, `error(code, message)`,
    `msg(from, text, ts = Date.now())`, `system(text, ts = Date.now())`,
    `users(users)`. Сервер вызывает `system('...')` с одним аргументом,
    а тесты проверяют, что `ts` — число;
- все константы, классы и функции — именованные экспорты (`export`);
- `encode(message)` и `decode(text)`. `decode` проверяет шаги 1–3 из 1.3
  и при ошибке **выбрасывает** `ProtocolError` с кодом `BAD_MESSAGE`
  (в отличие от `safeParseMessage`, которая возвращает результат).
  Тексты ошибок, как в эталоне: `'Message is not valid JSON'` (шаг 1)
  и `'Message must be a JSON object with a string "type" field'` (шаги 2–3);
- `isValidNick(nick)` — `true`, если это строка по правилу из упражнения 3;
- `validateText(text)` — возвращает `null`, если текст в порядке, или
  описание проблемы (эти тексты проверяют тесты эталона):

  | вход                                                 | результат                                  |
  | ---------------------------------------------------- | ------------------------------------------ |
  | не строка, пустая строка или одни пробелы (`trim()`) | `'Message must not be empty'`              |
  | длиннее `MAX_TEXT_LENGTH` символов (code points)     | `'Message is longer than 1000 characters'` |
  | остальное                                            | `null`                                     |

  Проверку на строку делайте первой: `[...text]` для `undefined`
  выбросит исключение.

**Проверка:** временный `check.js` в `chat/`:

```js
import { ServerMessage, decode, encode, isValidNick, validateText } from './protocol.js';

console.log(encode(ServerMessage.welcome(['ann']))); // {"type":"welcome","users":["ann"]}
console.log(decode('{"type":"msg","text":"hi"}')); // { type: 'msg', text: 'hi' }
console.log(isValidNick('ann'), isValidNick('ann!')); // true false
console.log(validateText('   ')); // Message must not be empty
try {
  decode('null');
} catch (error) {
  console.log(error.name, error.code); // ProtocolError BAD_MESSAGE
}
```
