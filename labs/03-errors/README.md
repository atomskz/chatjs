# Лабораторная 3. Ошибки и исключения

**Цель:** научиться выбрасывать, ловить и различать ошибки; отличать
ожидаемую ошибку (пользователь ввёл неправильный порт) от бага в коде;
не давать ошибке одной операции уронить всю программу.

**Примерное время:** 2 часа.

## Теория

### `throw` и `Error`

```js
throw new Error('Port is required');
```

Выбросить можно любое значение, даже строку, но принято бросать
объект `Error`: только у него есть стек вызовов (`error.stack`),
по которому видно, где случилась проблема.

Свойства ошибки:

| свойство  | что это                                               |
| --------- | ----------------------------------------------------- |
| `message` | текст для человека                                    |
| `name`    | вид ошибки: `Error`, `TypeError`, `SyntaxError`...    |
| `stack`   | стек вызовов — где ошибка создана                     |
| `cause`   | исходная ошибка, если эту создали «поверх» другой     |
| `code`    | у системных ошибок Node.js: `ENOENT`, `EADDRINUSE`... |

### `try / catch / finally`

```js
try {
  const data = JSON.parse(text); // может выбросить SyntaxError
  use(data);
} catch (error) {
  console.error(`Bad input: ${error.message}`);
} finally {
  cleanup(); // выполнится всегда: и после успеха, и после ошибки, и после return
}
```

Если объект ошибки не нужен, переменную можно не писать: `catch { ... }`.

### Свои классы ошибок

```js
export class ProtocolError extends Error {
  constructor(code, message) {
    super(message);
    this.name = 'ProtocolError';
    this.code = code; // машиночитаемый код: по нему решаем, что делать
  }
}
```

Свой класс позволяет вызывающему коду отличить «нашу» ожидаемую ошибку
от всех остальных:

```js
try {
  options = parseServerArgs();
} catch (error) {
  if (!(error instanceof UsageError)) throw error; // не наша — пробрасываем дальше
  console.error(`Error: ${error.message}\n${USAGE}`);
  process.exitCode = 1;
}
```

Строка `if (!(error instanceof X)) throw error` очень важна. Если поймать
всё подряд, баг (опечатка, `undefined.foo`) замаскируется под «неверные
аргументы», и искать его придётся долго.

### Обёртка ошибки и `cause`

Когда низкоуровневая ошибка ничего не говорит пользователю, её
заворачивают в свою, сохраняя исходную:

```js
throw new ValidationError(null, 'User must be valid JSON', { cause: error });
```

### Ожидаемые ошибки и баги

|             | ожидаемая ошибка                                   | баг                                         |
| ----------- | -------------------------------------------------- | ------------------------------------------- |
| пример      | порт занят, неверный JSON от клиента               | `TypeError: Cannot read properties of null` |
| кто виноват | внешний мир: пользователь, сеть, другая программа  | программист                                 |
| что делать  | понятное сообщение, продолжить или выйти с кодом 1 | залогировать стек, починить код             |

### Бросить исключение или вернуть результат?

Не каждая проблема — исключение. В эталонном проекте встречаются оба способа:

- `decode(text)` **выбрасывает** `ProtocolError`. Дальше работать
  с битым сообщением нельзя, а исключение само выходит из всех вложенных проверок;
- `validateText(text)` **возвращает** строку с описанием проблемы или `null`.
  Пустое сообщение — обычная ситуация, а не авария, и проверять результат
  через `if` проще, чем писать `try/catch`.

### Системные ошибки Node.js

Ошибки ввода-вывода приходят с полем `code`:

| код            | значит                                         |
| -------------- | ---------------------------------------------- |
| `ENOENT`       | нет такого файла или папки                     |
| `EACCES`       | нет прав                                       |
| `EADDRINUSE`   | порт уже занят                                 |
| `ECONNREFUSED` | по этому адресу никто не принимает подключения |
| `ETIMEDOUT`    | время ожидания истекло                         |
| `ENOTFOUND`    | имя хоста не найдено (DNS)                     |

Иногда Node.js пробует несколько вариантов подряд, например IPv4 и IPv6
для `localhost`, и тогда приходит `AggregateError`: сами ошибки лежат
в массиве `error.errors`.

### Необработанное исключение

Если исключение никто не поймал, Node.js печатает стек и завершает
процесс с кодом 1. Для сервера это значит, что один клиент с кривым
сообщением отключил бы всех. Поэтому обработку каждого входящего
сообщения оборачивают в **границу ошибок** — `try/catch`, который
логирует проблему и не пускает её дальше.

## Упражнения

Решения лежат в [solution/](solution/).

### Упражнение 1. Коды системных ошибок

Напишите `read-file.js <путь>`: прочитать файл через `readFileSync`
и вывести его длину. При ошибке вывести `error.code`, `error.syscall`
и человеческое сообщение для `ENOENT`, `EISDIR` и `EACCES`/`EPERM`,
а для остальных — `error.message`. Код выхода при ошибке — 1.

Проверьте на несуществующем файле, на папке (`.`) и на обычном файле.

### Упражнение 2. Свой класс ошибки

Напишите класс `ValidationError extends Error` с полем `field` и функцию
`parseUser(json)`, которая возвращает `{ name, age }` или выбрасывает
`ValidationError`:

- не JSON — `field: null`;
- нет `name` или это пустая строка — `field: 'name'`;
- `age` не целое неотрицательное число — `field: 'age'`.

Вызовите её для `'{"name":"Ann","age":30}'`, `'{"name":"Ann","age":-1}'`,
`'{"age":5}'` и `'not json'`. Ловите только `ValidationError`, остальное
пробрасывайте.

### Упражнение 3. Граница ошибок

Есть массив функций-задач: одна возвращает `'ok'`, вторая выбрасывает
`Error`, третья содержит баг `null.length`, четвёртая снова возвращает `'ok'`.
Выполните их все так, чтобы падение одной не мешало остальным,
и в конце выведите `Done, failed: 2 of 4`. Затем уберите `try/catch`
и посмотрите, что стало с процессом и его кодом выхода.

### Упражнение 4. `finally`

Напишите `withResource(action)`: печатает `open`, выполняет `action()`
и возвращает её результат, а `close` печатает в любом случае.
Проверьте на успешной функции и на функции, которая бросает исключение.
В каком порядке появились `close` и `result`?

### Упражнение 5. Цепочка причин

Доработайте `parseUser`: при неверном JSON оберните `SyntaxError` в
`ValidationError` с `{ cause: error }`, а при выводе ошибки печатайте
и причину.

## Шаг проекта

1. Доведите `main()` в `server.js` до такого вида: `UsageError` — сообщение,
   usage и `process.exitCode = 1`; любая другая ошибка пробрасывается
   (это баг, пусть будет виден стек).
2. Добавьте функцию `describeListenError(error, port)`. Она понадобится
   в лабораторной 10: для `EADDRINUSE` — «Port N is already in use...»,
   для `EACCES` — «No permission to listen on port N...», для остальных —
   `error.message`.
