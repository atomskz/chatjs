# Консольный чат на Node.js

Многопользовательский чат в терминале: один сервер, сколько угодно клиентов.
Работает на двух транспортах — WebSocket (библиотека [`ws`](https://github.com/websockets/ws))
и «голом» TCP (встроенный модуль `net`). Логика чата у обоих одна и та же.

Проект сопровождают [лабораторные работы](labs/): шестнадцать занятий,
после которых такой чат можно написать самому с нуля.

## Быстрый старт

Нужен Node.js 22 или новее.

```bash
npm install
```

Сервер (в одном терминале):

```bash
node server.js --port 5000
```

Клиенты (в других терминалах):

```bash
node client.js --host 127.0.0.1 --port 5000 --nick alice
node client.js --host 127.0.0.1 --port 5000 --nick bob
```

Чтобы подключиться с другой машины в локальной сети, укажите IP сервера,
например `--host 192.168.1.10`. Если не получается — проверьте, что брандмауэр
пропускает входящие подключения на этот порт.

### TCP-версия

Оба процесса запускаются с флагом `--transport tcp` (по умолчанию `ws`):

```bash
node server.js --port 5000 --transport tcp
node client.js --host 127.0.0.1 --port 5000 --nick alice --transport tcp
```

### Команды клиента

| команда  | что делает                |
| -------- | ------------------------- |
| `/users` | список участников         |
| `/quit`  | выйти (то же, что Ctrl+C) |
| `/help`  | список команд             |

### Тесты и проверка кода

```bash
npm test
```

Тесты поднимают настоящий сервер на случайном порту, подключают клиентов
программно и проверяют протокол: вход, рассылку, занятый ник, мусорные
сообщения, отключение. Весь набор прогоняется на обоих транспортах.

```bash
npm run lint
```

[ESLint](https://eslint.org) ищет ошибки в коде: неиспользуемые переменные,
опечатки в именах, недостижимый код.

```bash
npm run format
```

[Prettier](https://prettier.io) приводит оформление (отступы, кавычки, переносы)
к единому виду, чтобы в код-ревью не спорить о пробелах.
`npm run format:check` только проверяет, ничего не меняя.

## Архитектура

```
chatjs/
├── server.js              # точка входа сервера: аргументы, запуск, Ctrl+C
├── client.js              # точка входа клиента: аргументы, подключение
├── protocol.js            # формат сообщений и их проверка (общий для обеих сторон)
├── lib/
│   ├── chat-server.js     # логика сервера: участники, регистрация, рассылка
│   ├── chat-client.js     # логика клиента: вход, команды, реакция на сервер
│   ├── terminal-ui.js     # вывод в терминал и строка ввода (readline)
│   └── cli.js             # разбор аргументов командной строки
├── transport/
│   ├── index.js           # контракт транспорта + выбор реализации
│   ├── ws.js              # WebSocket
│   ├── tcp.js             # TCP + NDJSON
│   └── line-splitter.js   # нарезка TCP-потока на строки
├── test/
│   ├── helpers.js         # запуск сервера и программный клиент для тестов
│   └── *.test.js
├── eslint.config.js
└── .prettierrc.json
```

Слои и зависимости между ними (стрелка — «импортирует»):

```
 server.js ──► lib/chat-server.js ──┐
                                    ├──► protocol.js
 client.js ──► lib/chat-client.js ──┘
     │
     ├──► lib/terminal-ui.js          (readline)
     └──► transport/index.js ──► ws.js (ws) / tcp.js (net)
```

Главные решения:

- **Транспорт изолирован.** `ws` и `net` импортируются только в `transport/`.
  Наружу транспорт отдаёт простое «соединение»: `send(text)`, `close()`,
  события `message` и `close`. Контракт описан в начале
  [transport/index.js](transport/index.js). Логика чата (`lib/chat-*.js`)
  не знает, что под ней — WebSocket или TCP.
- **Протокол отделён от транспорта.** Транспорт передаёт строки,
  `protocol.js` превращает их в объекты и обратно и проверяет ники и тексты.
  Одни и те же правила используются и сервером, и клиентом.
- **Точки входа тонкие.** `server.js` и `client.js` только разбирают аргументы
  и связывают части между собой. Поэтому логику легко тестировать: тест
  создаёт `ChatServer` напрямую, без запуска процесса.
- **Ошибки не выходят за пределы соединения.** Транспорт сам перехватывает
  событие `error` сокета, а обработка каждого сообщения на сервере обёрнута
  в `try/catch`. Ошибка одного клиента не трогает остальных.
- **Один путь для выхода.** И `leave`, и обрыв связи приводят к событию
  `close`, а удаление участника и «X left the chat» происходят в одном
  обработчике.

В исходном ТЗ логика сервера лежит прямо в `server.js`. Здесь она вынесена
в `lib/`, чтобы её можно было импортировать из тестов, не запуская сервер.

## Протокол

Одно сообщение — один JSON-объект с полем `type`.

Клиент → сервер: `join {nick}`, `msg {text}`, `list`, `leave`.
Сервер → клиент: `welcome {users}`, `error {code, message}`,
`msg {from, text, ts}`, `system {text, ts}`, `users {users}`.

Коды ошибок: `BAD_MESSAGE` (не JSON / нет `type`), `UNKNOWN_TYPE`,
`NOT_JOINED`, `ALREADY_JOINED`, `INVALID_NICK`, `NICK_TAKEN`,
`INVALID_TEXT`, `INTERNAL_ERROR`.

## Ручная проверка

Отправить серверу произвольные сообщения по WebSocket:

```bash
npx wscat -c ws://localhost:5000
```

```
> hello
< {"type":"error","code":"BAD_MESSAGE","message":"Message is not valid JSON"}
> {"type":"msg","text":"hi"}
< {"type":"error","code":"NOT_JOINED","message":"Send \"join\" first"}
> {"type":"join","nick":"wscat"}
< {"type":"welcome","users":["wscat"]}
```

Проверка склейки сообщений на TCP-версии (`nc` есть в Linux и macOS;
в Windows можно использовать `ncat` из комплекта Nmap или WSL):

```bash
printf '{"type":"join","nick":"nc"}\n{"type":"msg","text":"hi"}\n' | nc localhost 5000
```

## Ответы на вопросы

### 1. Как устанавливается WebSocket-соединение?

Сначала открывается обычное TCP-соединение, и клиент отправляет по нему
обычный HTTP-запрос `GET` с заголовками `Connection: Upgrade`,
`Upgrade: websocket`, `Sec-WebSocket-Version: 13` и случайным ключом
`Sec-WebSocket-Key`. Сервер отвечает `101 Switching Protocols` и заголовком
`Sec-WebSocket-Accept` — это хеш от ключа клиента, так клиент убеждается,
что сервер действительно понимает WebSocket. После ответа HTTP на этом
соединении заканчивается, и по тому же TCP-соединению начинают ходить
WebSocket-фреймы. Если обратиться к нашему серверу обычным HTTP-запросом
без `Upgrade` (например, из браузера), он ответит `426 Upgrade Required`.

### 2. Что WebSocket добавляет к TCP?

TCP даёт надёжный упорядоченный **поток байтов** без границ. WebSocket сверху добавляет:

- **границы сообщений** — что отправили одним `send()`, то и придёт одним `message`;
- тип данных — текст (UTF-8) или двоичные данные;
- служебные фреймы: `ping`/`pong` для проверки, жив ли собеседник,
  и `close` с кодом причины для штатного закрытия;
- рукопожатие через HTTP — поэтому WebSocket проходит через прокси
  и работает в браузере, куда «голый» TCP не пускают.

### 3. Как один поток обслуживает 10 клиентов?

Сервер никогда не ждёт сеть «в лоб». Чтение и запись неблокирующие: Node.js
передаёт сокеты операционной системе (epoll в Linux, kqueue в macOS, IOCP
в Windows), а сам крутит **цикл событий** (event loop). Когда у какого-то
сокета появились данные, ОС сообщает об этом, и Node.js вызывает наш
обработчик. Обработчик быстро что-то делает и возвращает управление. Пока
клиенты молчат, поток просто спит и ничего не тратит.

В подходе «один поток на клиента» каждый поток блокируется на чтении из
своего сокета. Это просто писать, но каждый поток стоит памяти (стек)
и времени ОС на переключение, и на тысячах клиентов это дорого. Зато
в модели с циклом событий нельзя делать долгие синхронные вычисления
в обработчике: пока он работает, все остальные клиенты ждут.

### 4. Клиент закрыл терминал без `leave`

Когда процесс клиента завершается, ОС закрывает его сокеты: на сервер
приходит TCP-сегмент `FIN` (штатное закрытие) или `RST` (сброс). Для
WebSocket это закрытие без close-фрейма, с кодом 1006. На сервере в обоих
случаях срабатывает событие `close` соединения (иногда перед ним — `error`,
например `ECONNRESET`). Наш сервер обрабатывает `close` одинаково для любой
причины: удаляет участника и рассылает «X left the chat».

Если же связь пропала совсем (выдернули кабель), никакой пакет не придёт, и
сервер узнает об обрыве только при попытке отправить данные или по таймауту.
Для этого существуют heartbeat-проверки (ping/pong).

### 5. Почему `from` и `ts` ставит сервер?

Клиенту доверять нельзя: любой может подключиться через `wscat` и прислать
`{"type":"msg","from":"admin",...}`. Сервер знает, какой ник зарегистрирован
на этом соединении, — это единственный надёжный источник `from`. Время
тоже берётся у сервера: часы клиентов могут отличаться, и только так
у всех участников будет единый порядок сообщений. Проверка в тестах:
сервер игнорирует подделанные `from` и `ts`.

### 6. `127.0.0.1` или `0.0.0.0`?

`127.0.0.1` — это loopback, адрес «этого же компьютера». Сервер, который
слушает только его, доступен лишь программам на той же машине. `0.0.0.0`
означает «все IPv4-интерфейсы»: сервер принимает подключения на любой адрес
машины, в том числе на адрес в локальной сети, поэтому к нему можно
подключиться с другого компьютера. Наш сервер не указывает адрес вовсе —
тогда Node.js слушает все интерфейсы сразу и для IPv4, и для IPv6 (`::`).

## Дополнительное задание 11.1: переход на TCP

### Почему одно событие `data` — не одно сообщение?

TCP — это поток байтов, у него нет понятия «сообщение». Отправитель
и сеть вправе как угодно резать и склеивать байты: несколько маленьких
`write()` могут уйти одним пакетом (алгоритм Нейгла), большое сообщение
может прийти несколькими кусками, а ОС на стороне получателя отдаёт всё,
что успело накопиться в буфере. Поэтому получатель сам копит байты
и ищет границы сообщений — у нас это символ `\n`
([transport/line-splitter.js](transport/line-splitter.js)).

Отдельная ловушка — UTF-8: буква «П» занимает 2 байта, эмодзи — 4, и граница
куска может пройти посередине символа. Если декодировать каждый кусок
отдельно, получатся символы-заменители `�`. `StringDecoder` хранит неполный
символ до прихода следующего куска.

### Как теперь выглядит ответ на вопрос 2?

Теперь хорошо видно, что именно WebSocket делал за нас: нарезку на
сообщения пришлось написать самим (`LineSplitter`), а вместе с ней —
защиту от слишком длинной строки и сборку разорванных UTF-8 символов.
Штатного закрытия с кодом причины и ping/pong у нас нет: есть только
`end()` (FIN) и `destroy()`. Рукопожатия тоже нет — к TCP-серверу можно
подключиться чем угодно, хоть `nc`, но через HTTP-прокси или из браузера —
нельзя.

### Бонус: `\n` или префикс длины?

Здесь используется `\n`, префикс длины не реализован. Сравнение:

|         | разделитель `\n`                                | префикс длины (4 байта + данные)       |
| ------- | ----------------------------------------------- | -------------------------------------- |
| отладка | можно руками через `nc`                         | нужна программа, чтобы посчитать длину |
| данные  | не должны содержать `\n` (JSON это гарантирует) | любые, в том числе двоичные            |
| разбор  | ищем `\n` в буфере                              | читаем 4 байта, ждём ровно N байт      |
| память  | заранее неизвестно, сколько ждать               | сразу видно размер и можно отказать    |
